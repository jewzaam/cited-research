Build effort: 4-10 weeks for a production-ready system, primarily orchestration since the MCP servers already exist [187, 188]. Ongoing maintenance: 0.25-0.5 FTE/quarter [188].

Data touches exactly two external parties: Anthropic (for reasoning) and the target platform (for data). No intermediaries.

## 4. Per-Platform Integration Analysis

### 4.1 Jira: Status Monitoring & Action Detection

**What to surface:**

| Signal | JQL Pattern | Source |
|--------|------------|--------|
| Stale assigned tickets | `assignee = currentUser() AND statusCategory != Done AND updated < -7d` | [66, 67] |
| Approaching deadlines | `due <= startOfDay("+3d") AND due >= startOfDay() AND statusCategory != Done` | [70] |
| Overdue tickets | `assignee = currentUser() AND statusCategory != Done AND due < startOfDay()` | [70] |
| Blocked items | `issueLinktType = "is blocked by" AND status != Done` | [68] |
| Sprint items at risk | `Sprint in openSprints() AND statusCategory != Done AND assignee = currentUser()` | [72] |
| Status transitions | Poll `?expand=changelog`, filter `changelog.items` for `field === "status"` | [77, 80] |

**Key limitations:**
- No `statusChangedDate` in JQL — only `statusCategoryChangedDate` [73]
- No cross-field date comparison without marketplace apps [71]
- New `/rest/api/3/search/jql` endpoint has pagination bugs [65]
- Webhooks expire after 30 days and are best-effort [78]

**Recommended approach:** Polling via JQL as primary (via MCP `searchJiraIssuesUsingJql`), changelog inspection for detail, webhooks supplementary if infrastructure permits [80, 82].

### 4.2 GitHub: Activity Surfacing

**What to surface:**

| Signal | Method | Source |
|--------|--------|--------|
| PRs awaiting review | GraphQL `review-requested:USERNAME` | [96, 97] |
| Authored PRs with activity | GraphQL `author:USERNAME` + `updatedAt` check | [97, 98] |
| Failing CI on user's PRs | `statusCheckRollup.state` embedded in PR query | [99] |
| Assigned issues | GraphQL `assignee:USERNAME` | [97] |
| Mentions | GraphQL `mentions:USERNAME` | [97] |
| Stale PRs | `actions/stale` or custom time-based filtering | [107] |

GraphQL aliases allow combining all queries in one request [98]. `gh pr status` provides a quick personal dashboard [101].

**Key limitations:**
- Notifications API requires classic PAT — incompatible with fine-grained tokens [94]
- No server-side reason filter on notifications [94]
- CI status requires N+1 queries (per-PR) [100]
- `gh pr status` has a known bug: re-requested reviews show as "Approved" [103]

### 4.3 Google Workspace: Signal Extraction

**Gmail:**
- `messages.list` with `q=is:unread` for unread emails [113]
- `gmail.readonly` scope required (restricted — needs security assessment for production) [115, 116]
- Rate limit: 250 quota units/user/second [117]
- No native "awaiting response" detection — requires heuristic or LLM analysis

**Calendar:**
- No conflict detection endpoint — must list events and compare times [121]
- `calendar.events.readonly` scope sufficient [123]
- Push notifications available for efficient monitoring [122]

**Drive/Docs:**
- `comments.list` with `resolved` field for unresolved comments [126, 127]
- Suggestions readable via `suggestionsViewMode` but API cannot accept/reject [132, 133]
- Comments managed through Drive API, not Docs API [134]

**Key limitation:** No server-side @-mention filter for doc comments — requires client-side parsing [126].

### 4.4 Slack: Data Source

**Core approach:** `conversations.history` + `search.messages` for message retrieval; Events API for real-time monitoring [147, 148, 151].

**Critical constraint:** Non-Marketplace apps face **1 req/min, 15 messages/req** limits on both `conversations.history` and `conversations.replies` effective March 3, 2026 [155]. Internal customer-built apps are exempt, but a personal tool distributed outside the Marketplace is not.

**Mitigation options:**
1. Register as an internal customer-built app (if within a Workspace you administer)
2. Use the official Slack MCP server (GA Feb 2026) [49] — uses the Real-time Search API, different rate limits
3. Use `korotovsky/slack-mcp-server` in stealth mode [158] (but raises governance questions)

**Slack's native AI** already surfaces action items in the Activity view on paid plans [160, 161]. If the user has a paid Slack plan, leveraging Slack's own AI for action item extraction and using the MCP server for search/context may be more efficient than raw API access.

### Build Risks

1. **Token cost unpredictability:** Tool definitions consume 55-134K tokens before data processing begins [57]. Mitigated by Tool Search and prompt caching [57, 54].
2. **Auth complexity:** OAuth flows for 4 services require careful token management [41, 44, 48, 158].
3. **Maintenance:** APIs evolve; budget 0.25-0.5 FTE/quarter [188].
4. **AI cost overruns:** Organizations underestimate AI costs by 50%+ in 24% of cases [194].

### Hybrid Option

Claude Pro ($20/mo) + Cowork + read-only MCP servers [1, 31]:
- Setup: 1-2 weeks (configure MCP servers + write Cowork skill)
- Constraint: requires Claude Desktop running on local machine
- Advantage: no custom orchestration code; briefing interface included

### Recommendation

**Build with Claude API + Agent SDK + pre-built MCP servers.** Rationale:

1. **Cost:** $6-13/mo vs. $18-50+/mo for subscription alternatives
2. **Control:** Full control over what data is accessed, how it flows, and what actions are surfaced
3. **Privacy:** Data touches only Anthropic and the platform APIs — no third-party middleware [205]
4. **Fit:** No existing tool matches the advisory/read-only model with all five integrations [1]
5. **Feasibility:** All MCP servers exist; the Agent SDK was built for this use case [58, 60]

Start with Claude Pro + Cowork for rapid prototyping (hours, not weeks), then migrate to API + Agent SDK for production.

## 6. Privacy & Data Flow

### Where Data Goes

With Claude API + official MCP servers, data flows only between:

1. **Local machine** — MCP clients run locally via stdio transport [35]
2. **Platform APIs** — Jira, GitHub, Google Workspace, Slack (OAuth-scoped, read-only) [41, 44, 47, 49]
3. **Claude API** — 7-day retention, never used for training [197]; ZDR available for enterprise [198]

No intermediary routing services. No middleware. No third-party data processors beyond Anthropic and the platform providers [205].

### Data Egress Controls

1. Use official MCP servers only — 43% of public servers have vulnerabilities [207]
2. Enforce read-only mode: GitHub `--read-only` [44], korotovsky Slack read-only default [158], OAuth scope restriction for others [115, 123, 130]
3. Use Claude API (not consumer accounts) for 7-day retention and no-training guarantee [197]
4. Network controls: firewall to restrict outbound to only the five API endpoints
5. Audit MCP tool annotations (Nov 2025 spec) for read-only vs. write declarations [35]

### Consumer vs API Privacy Distinction

Claude Pro/Max (for Cowork) is a consumer account with weaker privacy defaults — retention up to 5 years unless you opt out; training possible if not opted out [197]. The API has a flat no-training policy and 7-day retention. **If privacy is paramount, use the API path, not Cowork.**

## 8. Limitations of This Analysis

1. **Token budget estimates are theoretical** — based on general token-per-content ratios, not measured against actual API responses [Section A, dim 7]
2. **Slack rate limit impact unclear** — the March 2026 change [155] may significantly constrain a personal tool not registered as internal
3. **No published reference implementation** — the pieces exist but nobody has published a complete advisory PA across all five platforms
4. **MCP ecosystem is young** — tool names, signatures, and capabilities are actively evolving [45]
5. **EU data residency gap** — Anthropic does not offer EU-hosted API endpoints directly
