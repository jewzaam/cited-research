Generated By: Claude Code (Claude Opus 4.6)

## Research Objective

Research approaches for monitoring Jira and surfacing actionable items. The PA should detect tickets assigned to the user that need attention (stale, blocked, approaching deadlines), status changes on watched tickets, new comments or mentions requiring response, sprint items at risk, blocker detection and escalation signals, and tickets that transitioned state and may need follow-up.

## 1. Jira REST API — Issue Search with JQL

### Endpoint

The primary search endpoint is `GET /rest/api/3/search/jql` (or POST for complex queries). The legacy `/rest/api/3/search` endpoint was deprecated and scheduled for removal after August 1, 2025.

- **Source URL:** https://developer.atlassian.com/cloud/jira/platform/rest/v3/api-group-issue-search/ (accessed 2026-03-26)
- **Source URL:** https://confluence.atlassian.com/jirakb/run-jql-search-query-using-jira-cloud-rest-api-1289424308.html (accessed 2026-03-26)

### Key Capabilities

- Accepts JQL queries to find issues matching arbitrary criteria
- Supports `fields` parameter to select specific fields in the response
- Supports `expand` parameter with values: `renderedFields`, `names`, `schema`, `operations`, `editmeta`, `changelog`, `versionedRepresentations`
- Pagination now uses `nextPageToken` instead of the deprecated `startAt` parameter
- Maximum results per request configurable (up to 100)

### Known Issues with the New Endpoint (Quality Concern)

Community reports indicate significant problems with the replacement endpoint: "Pagination is broken — `isLast` never returns true, `nextPageToken` chains endlessly, delivering thousands of new and unique tokens but always loading the first page again and again, leaving integrations in infinite loops."

- **Source URL:** https://community.atlassian.com/forums/Jira-questions/REST-The-new-rest-api-3-search-jql-endpoint-is-a-complete/qaq-p/3101716 (accessed 2026-03-26)
- **Quality note:** Community forum post with multiple corroborating replies. Indicates the new endpoint may have reliability issues for production use. The v2 endpoint may still be available as a fallback.

## 2. JQL Patterns for "Needs Attention" Detection

### Stale Tickets

JQL uses `updatedDate` and `statusCategoryChangedDate` for staleness detection. Key distinction: `updatedDate` triggers on any change (comment, field edit), while `statusCategoryChangedDate` only tracks transitions between status categories (To Do, In Progress, Done).

Example — tickets not updated in 7 days:
```jql
assignee = currentUser() AND statusCategory != Done AND updated < -7d
```

Example — tickets that haven't changed status category in 14 days:
```jql
assignee = currentUser() AND statusCategory = "In Progress" AND statusCategoryChangedDate < -14d
```

- **Source URL:** https://support.atlassian.com/jira/kb/how-to-search-using-statuscategory-statuscategorychangeddate-function-with-jql/ (accessed 2026-03-26)
- **Source URL:** https://community.atlassian.com/forums/Jira-questions/JQL-for-stale-issues-since-their-creation/qaq-p/1527827 (accessed 2026-03-26)
- **Quality note:** Atlassian's own KB article. The `statusCategoryChangedDate` function is documented but does not track individual status changes within the same category (e.g., moving between two "In Progress" statuses would not update it).

### Blocked Tickets

Basic blocker detection via issue links:
```jql
issueLinktType = "is blocked by" AND status != Done
```

For more advanced filtering (blocked by unresolved issues), third-party apps like "JQL Booster Pack" provide:
```jql
issue IN linkedIssuesOf('resolution IS EMPTY', 'blocks')
```

Alternatively, Jira's built-in "Flag" feature marks items having issues (shown in bright yellow on boards). Flagged issues are searchable via JQL.

- **Source URL:** https://community.atlassian.com/forums/Jira-questions/filter-out-all-blocked-issues/qaq-p/1400998 (accessed 2026-03-26)
- **Source URL:** https://medium.com/the-pinch/thou-shalt-not-have-a-blocked-status-in-jira-9bcafde684b8 (accessed 2026-03-26)
- **Quality note:** The Medium article argues against using a "Blocked" status at all, preferring flags. The community post confirms that native JQL cannot filter by linked issue resolution without third-party apps.

### Approaching Deadlines

```jql
assignee = currentUser() AND statusCategory != Done AND due <= startOfDay("+7d") AND due >= startOfDay()
ORDER BY due ASC
```

For overdue items:
```jql
assignee = currentUser() AND statusCategory != Done AND due < startOfDay()
```

JQL does not natively support comparing two date fields against each other (e.g., `statusCategoryChangedDate > duedate`). A marketplace app like "JQL Search Extensions for Jira" enables this with syntax like `issue in dateCompare("duedate < done")`.

- **Source URL:** https://saasjet.com/blog/top-18-jql-queries-to-use-every-day/ (accessed 2026-03-26)
- **Source URL:** https://community.atlassian.com/forums/Jira-Service-Management/JIRA-JQL-Query-to-find-issues-statusCategoryChangedDate-after/qaq-p/2363293 (accessed 2026-03-26)

### Sprint Items at Risk

```jql
Sprint in openSprints() AND statusCategory != Done AND due <= startOfDay("+7d") AND due >= startOfDay()
ORDER BY due ASC
```

Sprint membership query:
```jql
Sprint in openSprints() AND Sprint not in futureSprints() AND assignee = currentUser() AND statusCategory != Done
```

- **Source URL:** https://github.com/jscanzoni/jql (accessed 2026-03-26)
- **Quality note:** GitHub gist with curated JQL examples. Sprint-based queries depend on the project using Scrum boards with sprints configured.

### Limitation: No `statusChangedDate` in JQL

Currently only `statusCategoryChangedDate` is available — not `statusChangedDate`. This means you cannot natively query "tickets that changed to a specific status within the last N days." The community has requested this feature but it has not been implemented.

- **Source URL:** https://community.atlassian.com/forums/New-to-Jira-discussions/Jira-to-allow-using-StatusChangedDate-in-JQL/td-p/2258641 (accessed 2026-03-26)

## 3. Jira Webhooks for Real-Time Change Detection

### Available Events

Jira Cloud supports webhooks for the following event categories:

**Issue Events:**
- `jira:issue_created` — issue created
- `jira:issue_updated` — any field on an issue modified (including status transitions)
- `jira:issue_deleted` — issue deleted

**Comment Events:**
- `comment_created` — comment added
- `comment_updated` — comment edited
- `comment_deleted` — comment removed

**Sprint Events:**
- `sprint_created`, `sprint_updated`, `sprint_started`, `sprint_deleted`, `sprint_closed`

**Forge-Specific Events:**
- `avi:jira:assigned:issue` — user assigned or unassigned
- `avi:jira:mentioned:issue` — user mentioned in description

- **Source URL:** https://developer.atlassian.com/cloud/jira/platform/webhooks/ (accessed 2026-03-26)
- **Source URL:** https://developer.atlassian.com/platform/forge/events-reference/jira/ (accessed 2026-03-26)
- **Source URL:** https://inventivehq.com/blog/jira-webhooks-guide (accessed 2026-03-26)

### JQL Filtering on Webhooks

Webhooks can be scoped using a JQL filter to only fire for matching issues. However, sprint events (`sprint_*`) and version events (`jira:version_*`) do NOT support JQL filtering — the `jqlFilter` value is required in the payload but ignored.

### Webhook Payload — Changelog for Status Detection

The `jira:issue_updated` payload includes a `changelog` object with an `items` array. Each item contains: `field` (e.g., "status"), `fieldtype`, `fieldId`, `from`, `fromString` (e.g., "To Do"), `to`, `toString` (e.g., "In Progress").

To detect status changes specifically, filter changelog items where `field === "status"`.

- **Source URL:** https://gist.github.com/icelander/f598d036f3d3513f9acdc6112bf18933 (accessed 2026-03-26)
- **Quality note:** GitHub gist with an example payload. Real-world payloads may vary. A known issue is that when an issue is transitioned on a board, two webhook events may fire — one for status change and one for Rank change. Filter by checking the `field` value in the changelog.

### Webhook Reliability and Expiration

- Delivery is **best effort** — not guaranteed. If the receiving service is down, the event is lost.
- Webhooks registered via the REST API expire after **30 days** and must be refreshed using `PUT /rest/api/2/webhook/refresh`.
- Concurrency limits apply: 20 concurrent requests per tenant + webhook URL host pair for primary webhooks, 10 for secondary.

- **Source URL:** https://developer.atlassian.com/cloud/jira/platform/rest/v2/api-group-webhooks/ (accessed 2026-03-26)

### Registration Methods

1. **Jira Administration Console:** System > Webhooks (requires Jira admin permission)
2. **REST API:** `POST /rest/api/2/webhook` (requires Jira Administrators global permission)
3. **Connect App Descriptor:** Declare webhook modules in `atlassian-connect.json`

- **Source URL:** https://support.atlassian.com/jira-cloud-administration/docs/manage-webhooks/ (accessed 2026-03-26)

## 4. Issue Changelog API (Polling Approach)

For cases where webhooks are not available or reliable, the changelog can be polled:

- `GET /rest/api/3/issue/{issueIdOrKey}/changelog` — paginated list of all changelogs sorted by date (oldest first)
- `GET /rest/api/3/issue/{issueIdOrKey}?expand=changelog` — issue details with changelog embedded (most recent first)

The audit records API (`GET /rest/api/3/auditing/record`) tracks admin-level configuration changes, NOT issue updates. It is not suitable for monitoring ticket activity.

- **Source URL:** https://support.atlassian.com/jira/kb/how-to-analyze-the-history-or-changelog-of-an-issue-in-jira/ (accessed 2026-03-26)
- **Source URL:** https://community.atlassian.com/forums/Jira-questions/For-Jira-Cloud-s-Work-Item-s-Activity-section-which-REST-API/qaq-p/3150016 (accessed 2026-03-26)
- **Quality note:** Atlassian KB article. The changelog endpoint is reliable but requires polling individual issues — not efficient for monitoring many issues at scale. Combining with JQL search (to identify candidates) and then fetching changelogs for those issues is the practical pattern.

## 5. Jira Automation Rules (Built-in)

Jira's built-in Automation feature supports monitoring patterns without external tooling:

### Scheduled Trigger + JQL

Create rules that run on a schedule (e.g., daily) with JQL to find issues matching "needs attention" criteria. Example: find blocked issues not updated in 5+ days, then send a Slack notification and add a comment.

```
Trigger: Scheduled (daily)
JQL: status = "Blocked" AND updated < -5d
Actions: Send Slack message, Comment on issue, Transition issue
```

### Field Value Changed Trigger

Fires when any field value changes. Supports system and custom fields. Can be narrowed by change type: value added, value deleted, or any changes.

### Due Date Trigger

Automation can trigger based on due date proximity:
```
Trigger: Scheduled (daily)
JQL: duedate = startOfDay("+30d") AND resolution is empty
Actions: Send email to assignee, Add comment
```

### Auto-Close Stale Tickets

Template available for auto-closing issues in "Waiting for customer" status with no updates for N days.

- **Source URL:** https://www.atlassian.com/agile/tutorials/how-to-escalate-overdue-issues-with-jira-software-automation (accessed 2026-03-26)
- **Source URL:** https://www.atlassian.com/software/jira/automation-template-library/auto-close-jira-issues (accessed 2026-03-26)
- **Source URL:** https://support.atlassian.com/cloud-automation/docs/jira-automation-triggers/ (accessed 2026-03-26)
- **Quality note:** First-party Atlassian tutorials. Automation rules run within Jira Cloud's infrastructure and have execution limits based on plan tier.

### Limitation: Automation Cannot Prevent Actions

Automation can only react to events, not prevent them. Blocking a transition requires workflow validators/conditions, not automation rules.

- **Source URL:** https://community.atlassian.com/forums/Jira-questions/Automation-should-block-status-change/qaq-p/2336852 (accessed 2026-03-26)

## 8. Recommended PA Architecture for Jira Monitoring

Based on the research, a PA monitoring Jira would use a combination of:

1. **Polling via JQL** (primary): Periodic JQL queries via REST API or MCP `searchJiraIssuesUsingJql` to detect:
   - Stale assigned tickets (`assignee = currentUser() AND statusCategory != Done AND updated < -7d`)
   - Approaching deadlines (`due <= startOfDay("+3d") AND due >= startOfDay()`)
   - Blocked items (`issueLinktType = "is blocked by"`)
   - Sprint items at risk (`Sprint in openSprints() AND statusCategory != Done`)

2. **Webhooks** (supplementary, if infrastructure permits): For near-real-time detection of:
   - Status transitions (filter `changelog.items` for `field === "status"`)
   - New comments (`comment_created` event)
   - Assignment changes (`avi:jira:assigned:issue`)

3. **Changelog inspection** (targeted): For issues identified by JQL, fetch `?expand=changelog` to determine what changed and when.

### Gaps Identified

- **No native `statusChangedDate` in JQL** — can only track status category changes, not individual status transitions
- **No native cross-field date comparison in JQL** — cannot query "completed after due date" without marketplace apps
- **Webhook reliability** — best-effort delivery with 30-day expiration means webhooks alone are insufficient for critical monitoring
- **New search endpoint instability** — community reports of pagination bugs in the replacement `/rest/api/3/search/jql` endpoint
- **No activity stream API for personal feed** — Jira does not expose a personal activity stream via REST API that aggregates "things that need my attention"
