# Hook and Permission System Gaps

Generated By: Claude Code (Claude Opus 4.6)

**Dimension:** General categories of risk that hook/permission systems in AI coding assistants do NOT cover
**Sources:** See [../hook-gaps-citations.md](../hook-gaps-citations.md)

## 1. Indirect Prompt Injection via Tool Results

Hooks inspect commands, not the semantic content of data returned by allowed tools. File reads, web fetches, and API responses can contain instructions that redirect the AI.

- OWASP ranks prompt injection as #1 critical vulnerability for LLM applications [HG-1]
- Root cause: "inherent lack of distinction between instructions and data in LLMs" [HG-1]
- Nasr et al. (2025, joint OpenAI/Anthropic/Google DeepMind) demonstrated every published defense was bypassed at >90% by adaptive attackers [HG-2]
- Simon Willison: "I am deeply suspicious of [guardrail products] — they typically claim '95% of attacks' captured, but in web application security, 95% is very much a failing grade" [HG-3]

## 2. Data Exfiltration Through Allowed Channels

Data can leak through operations hooks permit:

| Channel | How it works | Source |
|---------|-------------|--------|
| Git commits/PRs | AI creates PRs containing private repo data, triggered by prompt injection in public issues | Docker/Invariant Labs [HG-4] |
| Image URL encoding (CamoLeak) | Hidden prompts instruct AI to encode secrets character-by-character as image URLs | WindowsForum [HG-5] |
| DNS queries | Even "air-gapped" sandboxes vulnerable to DNS-based exfiltration | SnailSploit [HG-6] |
| File writes | Auto-approved workspace file writes can modify config files, enabling RCE | Bright Security [HG-7] |
| AI service API requests | Data included in requests to the AI model's own API | Trend Micro [HG-8] |

## 3. TOCTOU (Time-of-Check-Time-of-Use) Race Conditions

Hook-based "check then execute" patterns fail when the checked artifact differs from the executed artifact.

**Cursor TOCTOU** (Arnica, March 2025) [HG-9]: Agent inspects a script before executing it, but execution fetches a fresh copy. Malicious server delivers benign script during inspection, malicious during execution.

**Gemini CLI MemoryTool** [HG-10]: TOCTOU in the approval pipeline. File read during `getConfirmationDetails`, cached string written during `execute`. Another process can modify the file between approval and write.

**Key insight:** "Safety mechanisms built on script inspection can fail if the inspected artifact is not guaranteed to be the artifact that is executed" [HG-9].

## 4. Regex/Pattern-Matching Evasion

Shell command filtering via regex is defeated by multiple techniques [HG-11]:

| Technique | Example | Result |
|-----------|---------|--------|
| `$IFS` substitution | `cat${IFS}/etc/passwd` | `cat /etc/passwd` |
| Uninitialized variable | `c${x}at /etc/passwd` | `cat /etc/passwd` |
| Wildcard/globbing | `/bin/?at /etc/passwd` | `cat /etc/passwd` |
| Quote splitting | `c'at' /'e''t'c/passwd` | `cat /etc/passwd` |
| Brace expansion | `{cat,/etc/passwd}` | `cat /etc/passwd` |
| Env var substring | `${PATH:0:1}` extracts `/` | Reconstruct blocked commands |
| Automated obfuscation | Bashfuscator, DOSfuscation | Generate undetectable variants |

These techniques bypass CloudFlare WAF and ModSecurity OWASP CRS3 [HG-11].

## 5. Configuration File Weaponization

Project configuration files are treated as metadata but function as execution vectors.

**CVE-2025-54135 (CurXecute)** [HG-12]: Creating a new `.cursor/mcp.json` bypasses approval. With auto-run enabled, injected commands execute immediately. CVSS 8.6.

**CVE-2025-59536** [HG-13]: Three attack vectors through Claude Code project configuration:
1. Malicious hooks in `.claude/settings.json` — any contributor with commit access can inject
2. MCP consent bypass via `enableAllProjectMcpServers`
3. API key theft via `ANTHROPIC_BASE_URL` redirect (CVE-2026-21852)

**CVE-2025-55284** [HG-12]: Claude Code allowlist bypass. CVSS 7.1. Overly broad safe command list enabled unauthorized file reading and network exfiltration. Fixed in v1.0.4.

**Key quote** (Check Point): "Configuration files effectively become part of the execution layer. What was once considered operational context now directly influences system behavior" [HG-13].

## 6. The Confused Deputy Problem

The AI agent operates with user-level permissions but acts on instructions from untrusted sources.

- LLMs that resist direct malicious commands will execute identical payloads when requested by peer agents [HG-14]
- "A useful rule is to treat every tool call as a privileged API request that happens to be proposed by a language model" [HG-14]
- ⚠️ Specific percentages (41.2%, 52.9%, 82.4%) previously cited from Quarkslab could not be independently verified by citation audit — treat as unverified

## 7. Multi-Agent Trust Escalation

LLMs that resist direct malicious commands execute identical payloads when requested by peer agents. Hook systems do not model inter-agent trust boundaries [HG-14].

## 8. Tool Description Poisoning

MCP tool descriptions are added to the model's context and can contain hidden instructions that redirect behavior before any tool is called. 84.2% success rate with auto-approval enabled. This operates entirely outside the hook inspection layer [HG-15].

**Swap attack (CVE-2025-54136)**: Attacker submits harmless command for approval, then replaces plugin with malicious payload without re-scrutiny [HG-15].

## 9. Command Encapsulation Bypass

Hooks inspect the command Claude runs, not the commands *that command runs*. PreToolUse hooks receive a JSON payload with `tool_input.command` as a string and pattern-match against it — no mechanism exists to inspect child processes [EB-1]. Any allowed command that internally invokes blocked operations bypasses the hook layer entirely.

**Example:** A PreToolUse hook blocks `pip install`. But `make test` is allowlisted. If the Makefile target runs `pip install -e .[dev]` as a prerequisite, dependencies are installed without the hook ever seeing `pip`.

NVIDIA's AI Red Team explicitly documents this as a known attack pattern: "Attackers often use indirection — calling a more restricted tool through a safer, approved one — as a common way to bypass application-level controls such as allowlists" [EB-3]. They further note: "Once control passes to a subprocess, the application has no visibility into or control over the subprocess" [EB-3].

This generalizes across all encapsulation layers:

| Allowed command | What it can hide |
|----------------|-----------------|
| `make <target>` | Any shell command in the Makefile recipe |
| `npm run <script>` | Whatever `package.json` scripts defines |
| `docker build` | All `RUN` directives in the Dockerfile |
| `./script.sh` | Arbitrary commands inside the script |
| `python -m pytest` | conftest.py fixtures that install packages or fetch URLs |

GitHub Copilot CLI has partial sub-command matching for some commands (git, gh) but not general-purpose restriction — feature request #2037 identifies that allowing `shell(deno:*)` also permits install subcommands with no way to restrict to specific ones [EB-6]. Codex CLI uses the same two-layer model (approval + sandbox) [EB-7].

**Real-world exploitation:** The Nx malicious npm package weaponized local AI coding agents (Claude, Gemini, Q) via prompts to inventory sensitive files and exfiltrate data [EB-5]. David Wong identified that each major AI CLI has a permission-bypass flag and warned that poisoned repo config files (CLAUDE.md, GEMINI.md) could trigger agents to execute with those flags [EB-4].

### Sandbox as Partial Mitigation

Claude Code's OS-level sandbox (bubblewrap/Seatbelt) does apply to child processes: "These OS-level restrictions ensure that all child processes spawned by Claude Code's commands inherit the same security boundaries" [EB-2]. This means a Makefile running `pip install malicious-package` would be blocked from network access (if network isolation is active) and from writing outside the working directory.

However, sandboxing is not enabled by default — it must be activated via the `/sandbox` command [EB-2]. And NVIDIA warns: "many agentic systems only apply sandboxing at the time of tool invocation... many agentic functionalities default to running outside the sandbox, including hooks, MCP configurations that spawn local processes, and scripts used by 'skills'" [EB-3].

### Mitigation Options

- **OS-level sandbox with network isolation** — prevents any subprocess from fetching packages [EB-2]
- **PostToolUse hooks that diff lockfiles** (package-lock.json, poetry.lock) after every Bash command — detects but cannot prevent changes [EB-9]
- **Kernel-level interception** (e.g., agentsh) — enforces policy via seccomp/ptrace/FUSE at the system call level [EB-8]
- **Makefile recipes that separate install and test phases**, with hooks on each
- `--ignore-scripts` flags on package managers invoked by Makefile targets

Trail of Bits characterizes the hook model: "PreToolUse hooks are for prevention. PostToolUse hooks are for observation." PostToolUse cannot prevent actions [EB-9].

## 10. Allowlist Over-Breadth

CVE-2025-55284 demonstrated that even Claude Code's own safe command allowlist was too broad, enabling file reads and network exfiltration without confirmation. Determining what is "safe" in an agentic context differs fundamentally from what is safe under human control [HG-12].

## Architectural Defenses (Research)

**The "Lethal Trifecta"** (Willison) [HG-3]: An agent should never combine: (1) access to private data, (2) exposure to untrusted content, (3) ability to communicate externally.

**The "Agents Rule of Two"** (Ayzenberg, Meta AI) [HG-16]: Extends the Lethal Trifecta — an agent should never combine more than two of three dangerous properties.

**Design patterns with provable resistance** (Tramer et al., June 2025) [HG-16]:
- **Action-Selector**: LLM never sees tool output
- **Plan-Then-Execute**: Action sequence locked before untrusted data processed
- **LLM Map-Reduce**: Isolated sub-agents process external data
- **CaMeL**: Capability-based security with explicit control/data flow separation
