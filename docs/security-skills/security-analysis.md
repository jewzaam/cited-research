## 1. Threat Model: What Can Go Wrong

### 1.1 Supply Chain Attacks Are Accelerating

The software supply chain is under sustained attack, and AI coding assistants amplify the risk by adding dependencies faster than humans can evaluate them.

**Scale:** Sonatype's cumulative count of malicious open-source packages reached 877,522 by Q3 2025, with a 140% year-over-year surge [SC-17] (up from 156% YoY reported in October 2024 [SC-15]). Data exfiltration is the most common malicious behavior [SC-18].

**Attack vectors proven in the wild:**

| Attack Type | Real Example | Scale |
|-------------|-------------|-------|
| Typosquatting | PyPI mass upload forced registration suspension | 500+ packages, March 2024 [SC-1] |
| Dependency confusion | Birsan breached Apple, Microsoft, 33 others | $130K+ in bounties [SC-6] |
| Maintainer compromise | @solana/web3.js spear-phished | $160K stolen, CVE-2024-54134 [SC-11] |
| Social engineering | event-stream maintainer handoff | 8M downloads while compromised [SC-10] |
| Protestware | node-ipc overwrote files on Russian IPs | Affected Vue.js ecosystem [SC-20] |
| Install scripts | Shai-Hulud self-replicating worm | 796 packages, 132M monthly downloads [SC-22] |
| Slopsquatting | LLMs hallucinate package names at 5.2-21.7% | 205K unique hallucinated names, 58% repeated across runs [SC-23] |

**AI-specific amplifier — slopsquatting:** LLMs hallucinate non-existent package names at measurable rates (5.2% commercial, 21.7% open-source models). 58% of hallucinated names reappear across repeated runs, making them predictably exploitable. Attackers can register these names with malicious code before developers encounter the same hallucination [SC-23].

### 1.2 AI-Generated Code Is Less Secure Than Human Code

| Study | Finding | Source |
|-------|---------|--------|
| CodeRabbit (2025) | AI code 1.7x more issues overall; 2.74x more XSS | [5] |
| Veracode (2025) | AI code 2.74x more security flaws than human code | [6] |
| Perry et al. (Stanford) | Users with AI assistants wrote significantly less secure code AND believed it was MORE secure | [1] |
| Iterative feedback | Feeding SAST results back to LLM reduced vulnerability rate from 40.2% to 7.4% | [18] |

The most dangerous finding is the **confidence gap**: developers using AI assistants believe their code is more secure while it is actually less secure [1]. This creates a systematic under-investment in review.

**Common CWE patterns in AI code:** CWE-79 (XSS), CWE-89 (SQL injection), CWE-78 (OS command injection), CWE-22 (path traversal), CWE-798 (hardcoded credentials), CWE-502 (unsafe deserialization). See [reference/cwe-patterns-llm.md](reference/cwe-patterns-llm.md).

### 1.3 AI-Generated Tests Create False Confidence

AI-generated tests achieve broader code coverage (75% vs 60%) but shallower fault detection (80% vs 90% bug detection rate) [13]. Critical failure modes:

| Failure Mode | Description |
|-------------|-------------|
| Tautological assertions | Tests that pass by construction (asserting what the code does, not what it should do) |
| Coverage ≠ quality | A test suite can have 100% coverage but only 4% mutation score [27] |
| Circular validation | AI writes both code and tests — bugs in logic are mirrored in tests [7][19][20] |
| Broken tests | Without existing test context, 92.45% of Copilot-generated tests are failing/broken/empty [8] |

**Key statistic:** 42% of committed code is AI-generated, but fewer than half of developers review it before committing [12].

### 1.4 External Resources Are Attack Vectors

Claude Code with WebFetch + MCP satisfies Simon Willison's "Lethal Trifecta" — all three conditions for data theft [ER-17]:
1. Access to private data (filesystem, credentials)
2. Exposure to untrusted content (WebFetch, MCP tool results, repo content)
3. Ability to communicate externally (WebFetch, MCP servers, bash)

**MCP server ecosystem risks:**
- Anyone can publish an MCP server; 13,000+ exist [ER-2]
- 1,800+ found without authentication [ER-2]
- 53% use insecure long-lived credentials [ER-3]
- First confirmed malicious MCP server (postmark-mcp) found September 2025 [ER-12]
- 36.82% of 3,984 Claude Code skills contain security flaws (Snyk ToxicSkills) [ER-11]

**Prompt injection remains unsolved:** All 12 published defenses were bypassed at >90% success rate by adaptive attackers (joint OpenAI/Anthropic/Google DeepMind research) [ER-5]. OpenAI states it is "unlikely to ever be fully 'solved'" [ER-16].

### 1.5 Hook and Permission Systems Have Structural Gaps

Ten categories of risk that hook/permission systems do NOT address [HG-1 through HG-16]:

1. **Indirect prompt injection via tool results** — hooks inspect commands, not data semantics
2. **Exfiltration through allowed channels** — git commits, file writes, DNS, image URLs, API requests
3. **TOCTOU race conditions** — checked artifact differs from executed artifact (demonstrated in Cursor and Gemini CLI)
4. **Regex evasion** — $IFS substitution, variable injection, globbing, quote splitting, brace expansion
5. **Configuration file weaponization** — .claude/settings.json as execution vector (CVE-2025-59536, CVSS 8.7)
6. **Confused deputy** — AI acts on injected instructions while having legitimate permissions
7. **Multi-agent trust escalation** — LLMs resist direct injection but comply when peer agents request the same action
8. **Tool description poisoning** — hidden instructions in MCP tool descriptions (84.2% success with auto-approval)
9. **Command encapsulation bypass** — hooks inspect the command Claude runs, not the commands *that command runs* [EB-1]. `make test` is allowlisted; the Makefile can run `pip install` internally without the hook ever seeing it. NVIDIA's AI Red Team documents this as a known attack pattern [EB-3]. Generalizes to `npm run`, `docker build`, shell scripts, and any wrapper command. Real-world exploitation demonstrated via the Nx malicious package [EB-5]. Claude Code's OS-level sandbox mitigates this for network/filesystem access but is not enabled by default [EB-2].
10. **Allowlist over-breadth** — CVE-2025-55284 demonstrated Claude Code's own allowlist was too broad

## 3. Gap Analysis

### 3.1 Dependency Risk (Your Stated Blind Spot)

**Current state:** You have no automated dependency scanning. When Claude adds an `npm install` or `pip install`, you have no way to assess whether the package is:
- Known-vulnerable (CVE database)
- Malware (behavioral analysis)
- Typosquatted (name similarity)
- Hallucinated by the LLM (slopsquatting)

**Tool landscape:**

| Tool | npm | Python | Known CVEs | Malware Detection | Free CLI | Key Limitation |
|------|-----|--------|------------|-------------------|----------|----------------|
| npm audit | ✅ | ❌ | ✅ | ❌ | ✅ | CVEs only, no behavioral analysis |
| pip-audit | ❌ | ✅ | ✅ | ❌ | ✅ | CVEs only, Apache 2.0, PyPA official |
| Socket.dev | ✅ | ✅ | ✅ | ✅ | ✅ (free tier) | Behavior analysis, but vendor claims unverified |
| Snyk | ✅ | ✅ | ✅ | Partial | ✅ (limited) | 400 SCA tests/month free, proprietary DB |
| OSV.dev | ✅ | ✅ | ✅ | ❌ | ✅ (API) | Aggregates multiple DBs, Google-backed |
| Phylum/Veracode | ✅ | ✅ | ✅ | ✅ | ❌ | Enterprise-only since Phylum acquisition |
| Dependabot | ✅ | ✅ | ✅ | ❌ | ✅ (GitHub) | GitHub-only, no behavior analysis |

**No single tool covers all threat categories.** The biggest gap is behavior analysis — tools like npm audit and pip-audit structurally cannot detect malicious packages, typosquatting, or dependency confusion. Only Socket.dev (free tier available) and Veracode SCA (enterprise) provide this [Dep-ref: cross-tool-comparison.md].

**pip-audit has replaced Safety as the recommended Python scanner** due to Safety's restrictive CC BY-NC-SA 4.0 licensing and mandatory telemetry [Dep-ref: safety-pyup.md].

**Package signing is early-stage:** npm provenance (Sigstore) is GA since October 2023 but adoption data is limited. PEP 740 attestations launched November 2024 with ~5% of top 360 packages, and pip/uv cannot verify attestations at install time yet [Dep-ref: npm-provenance-sigstore.md, python-package-signing.md].

### 3.2 Deterministic Security Enforcement

**Core problem:** Skills trigger probabilistically (LLM description matching). A security skill that should fire on every `npm install` might not. Community observation: "Claude Code often ignores available skills entirely" [DS-15].

**Current mechanism hierarchy:**

| Mechanism | Determinism | Scope |
|-----------|------------|-------|
| OS sandbox | Deterministic | Filesystem + network isolation |
| Managed settings | Deterministic | Cannot be overridden by user/project |
| PreToolUse hooks | Deterministic | Fire on every matching tool invocation |
| PostToolUse hooks | Deterministic | Fire after every matching tool execution |
| Permission rules | Deterministic | Allow/deny per tool pattern |
| CLAUDE.md rules | Advisory only | No enforcement — model may ignore |
| Skills | Probabilistic | Trigger depends on LLM matching description |

**Key finding:** PreToolUse hooks are the ONLY mechanism for mandatory security checks that: (1) fire deterministically, (2) can block actions, and (3) operate independent of LLM reasoning [DS-1].

**No vendor has shipped policy-as-code integration** (OPA/Rego) for AI coding assistants. Enforcement remains in imperative shell scripts [DS-ref: policy-as-code-ai-agents.md].

**The denylist model is a fundamental limitation:** Current systems enumerate what to block (unbounded) rather than what to permit (bounded). A community proposal for allowlist-only immutable manifests exists but is unimplemented [DS-14].

### 3.3 Code and Test Quality

**Gap:** No automated gate between AI code generation and code acceptance. The iterative feedback loop (feeding SAST results back to the LLM) reduces vulnerabilities from 40.2% to 7.4% [18] but requires manual orchestration.

**Gap:** No mutation testing in your workflow. Code coverage is a poor proxy for test quality — 100% coverage can coexist with 4% mutation score [27]. Mutation-guided test generation (MuTAP) achieves 94% mutation score vs 66% for coverage-driven [2].

## 4. Recommendations

Ordered by impact-to-effort ratio, with the goal of removing blockers to faster development.

### Priority 1: Dependency Scanning via PreToolUse Hook (High Impact, Medium Effort)

Write a PreToolUse hook that intercepts `npm install` and `pip install` commands and runs dependency scanning before allowing the install.

**Recommended tool stack:**
- **npm:** `npm audit` (free, built-in) + Socket.dev CLI (free tier, behavioral analysis)
- **Python:** `pip-audit` (free, PyPA official, Apache 2.0)
- **Both:** OSV.dev API for cross-ecosystem CVE lookup

**Why PreToolUse hook:** This is the only mechanism that fires deterministically on every matching Bash command, regardless of what the LLM decides to do. It cannot be bypassed by prompt injection or skill non-triggering.

**Implementation sketch:** Hook matches `Bash`, inspects command for `npm install`/`pip install`, extracts package name, queries OSV.dev API and/or runs `npm audit`/`pip-audit` on the lockfile, blocks if critical/high vulnerabilities found.

### Priority 1b: Lockfile Diff via PostToolUse Hook (High Impact, Low Effort)

A PreToolUse hook on `pip install` is necessary but insufficient — `make test`, `npm run build`, `docker build`, and shell scripts can install dependencies without the hook ever seeing the package manager invocation. This is a fundamental single-layer limitation of command inspection, documented by NVIDIA's AI Red Team as a known attack pattern [EB-3] and confirmed by Claude Code's hooks architecture [EB-1].

Claude Code's OS-level sandbox mitigates this for network/filesystem access when enabled [EB-2], but sandboxing is not on by default and does not inspect what commands run — it restricts what files/network they can reach.

**Mitigation:** A PostToolUse hook on `Bash` that diffs lockfiles (package-lock.json, poetry.lock, uv.lock, requirements.txt) after every command. If a lockfile changed, the hook reports what was added and can trigger scanning. This catches encapsulated installs regardless of how deep the command nesting goes. Trail of Bits confirms PostToolUse hooks serve an observation role — they detect but cannot prevent [EB-9].

**Why this complements Priority 1:** Priority 1 catches direct `pip install`/`npm install`. This catches everything Priority 1 misses — Makefile targets, scripts, CI wrappers. Together they cover both layers.

### Priority 2: SAST Feedback Loop via PostToolUse Hook (High Impact, Medium Effort)

Run static analysis after every file write/edit and feed results back to Claude.

**Recommended tools:**
- **Python:** Bandit (47 checks including AI-specific B614/B615), Semgrep
- **JavaScript/TypeScript:** Semgrep, ESLint security plugins
- **Cross-language:** Semgrep (30+ languages, 20K+ rules, free community edition)

**Why PostToolUse hook:** Fires after every Edit/Write, can inject SAST findings into the conversation context. This implements the iterative feedback loop that reduced vulnerability rates from 40.2% to 7.4% [18].

### Priority 3: Mutation Testing Gate for AI-Generated Tests (Medium Impact, Low Effort)

Add mutation testing to your `make test` target to catch tautological tests and circular validation.

**Recommended tools:**
- **Python:** mutmut (maintained, pytest-compatible)
- **JavaScript/TypeScript:** Stryker (mature, widely adopted)

A mutation score threshold (e.g., >60%) as a Makefile target gives you a deterministic quality gate.

### Priority 4: MCP Server Audit and Lockdown (High Impact, Low Effort)

1. Review every MCP server in your configuration
2. Run MCP servers in Docker containers (prevents full user access inheritance)
3. Disable `enableAllProjectMcpServers`
4. Add `.claude/settings.json` and `.mcp.json` to your `block_paths.py` for repositories you don't own

### Priority 5: Enhance block_commands.py for Evasion Resistance (Medium Impact, Medium Effort)

Your current regex patterns are vulnerable to shell evasion techniques ($IFS substitution, variable injection, globbing, quote splitting) [HG-11]. Consider:
- Normalizing commands before matching (expanding variables, resolving globs)
- Using a shell parser (shlex + AST) rather than regex for command classification
- Adding a PostToolUse hook that verifies what actually executed matches what was approved (mitigates TOCTOU)

### Priority 6: Configuration File Protection (Medium Impact, Low Effort)

Add to `block_paths.py`:
- `.claude/settings.json` in cloned/external repos (prevents CVE-2025-59536)
- `.mcp.json` in cloned/external repos
- `.cursor/mcp.json`, `.vscode/settings.json` if you use those editors

### Priority 7: Slopsquatting Detection (Medium Impact, Medium Effort)

Add a check in the dependency scanning hook: before installing a package, verify it exists on the registry AND has a minimum age/download threshold. Brand-new packages with zero history are the primary slopsquatting vector.

## 5. What You Cannot Fully Mitigate

These risks have no complete solution. Acknowledge and manage residually:

1. **Prompt injection** — All 12 published defenses bypassed at >90% by adaptive attackers [ER-5]. Defense-in-depth reduces but does not eliminate risk. Accept that the AI may occasionally act on injected instructions.

2. **Confused deputy** — The AI operates with your permissions but processes untrusted content. No hook can distinguish legitimate user intent from injected instructions at the authorization level [HG-14].

3. **Zero-day malicious packages** — Even behavioral analysis tools like Socket.dev have detection gaps. The 7-14 day adoption delay for new packages/versions remains the most reliable defense [SC-21].

4. **Multi-agent trust escalation** — If you use sub-agents, they can be manipulated into requesting actions the primary agent would refuse [HG-14]. No current tool models inter-agent trust boundaries.

5. **Tool description poisoning** — MCP tool descriptions can contain hidden instructions that operate entirely outside hook inspection [HG-15]. Auditing tool descriptions manually is the only current defense.

## 6. Limitations of This Research

1. **WebFetch was denied for most agents** — the majority of citations are from WebSearch summaries, not verified full-page extractions. Citation audit agents will flag inaccessible sources.

2. **Vendor-reported accuracy metrics are marketing** — Snyk's "3x more vulnerabilities," Socket's "80% false positive reduction," and Veracode's "60% more accurate" are self-reported with no independent verification found.

3. **Landmark code security studies used deprecated models** — Perry et al. and Pearce et al. tested Codex and ChatGPT-3.5, not current Claude/GPT-4o models. Vulnerability rates may differ for modern models.

4. **Sonatype malicious package counts** are self-reported by a vendor with commercial interest. Methodology is not fully public.

5. **No specific analysis of your hook code was performed** for dimension 7 (per your request for general analysis). Specific bypass testing would require a separate engagement.

6. **AI-generated test trust research** is thinner on peer-reviewed sources than other dimensions — this is an area where practitioner experience outpaces academic study.
