# Browser-accessible coding shells — research

## Overview

The asker runs a self-hosted 3-node k3s homelab and wants ~12 concurrent browser-accessible AI-coding sandboxes — one Pod per operator, PVC-backed `$HOME`, reachable from any tailnet device by a single URL. This research covers only the access layer.

Of the five candidates surveyed, **NVIDIA OpenShell** and **OpenClaw** are wrong-category: OpenShell is an agent sandbox runtime (no browser TTY), OpenClaw is a personal AI assistant in a messaging-app shape. Of the four real browser-TTY tools — ttyd, gotty (sorenisanerd fork), wetty, code-server — **ttyd** is the most boring and lowest blast radius: a 6.9 MB Alpine image, an explicit `--auth-header X-WEBAUTH-USER` integration for upstream proxies, no opinions about multi-tenancy. **Wetty** is disqualified by an unfixed Origin-header vulnerability and a stale release lineage; **code-server** is disqualified by per-pod resource floor (≥1 GB RAM, 265 MB image) and Coder's own positioning that it is not designed for multi-user deployments. **Gotty** is a near-second to ttyd with stronger isolation defaults but a fork-of-archived-project lineage.

The recommended deployment shape is one Deployment + Service + Ingress + PVC per operator, generated by an Argo CD **ApplicationSet List** generator, fronted by the **Tailscale Operator's** Ingress class for single-URL-per-sandbox over MagicDNS, with optional oauth2-proxy sidecar terminating identity into ttyd's `X-WEBAUTH-USER` header pattern. Do not use the archived `kubernetes/ingress-nginx`; Traefik (k3s default) handles WebSocket out of the box.

See [`citations.md`](citations.md) for the source table; reference files in [`references/`](references/) contain per-dimension detail.

## Framing & out-of-scope

The brief frames "browser-accessible coding sandbox" as the design center. Three assumptions are worth surfacing:

1. The question presumes a browser-TTY shape. An alternative shape — exposing `kubectl exec` over a WebSocket gateway, or a code-server-style IDE-in-browser — is implicitly ruled out. The synthesis below considers all three and lands on browser-TTY for the lowest-friction starting point.
2. Managed sandbox services (Gitpod, Coder Cloud, GitHub Codespaces) are excluded by the self-hosted homelab framing. This is a deliberate scope choice but means the comparison does not benchmark against the hosted-service quality bar.
3. Per-sandbox identity (authn _after_ Tailscale ACLs gate the URL) is out of scope per the brief. The recommendation below treats this as a future decision; the chosen runtime (ttyd) integrates with oauth2-proxy via a documented header-pass-through pattern when the operator decides to add identity-aware logging.

## 1. OpenShell — direct profile

The right "OpenShell" for this framing is **NVIDIA/OpenShell** [1], announced at GTC 2026 [3]. It is _not_ a browser-TTY runtime — operator interaction is CLI (`openshell sandbox create`, `openshell policy set`) with an optional keyboard-driven TUI dashboard for monitoring [1]. The README is explicit that the project is alpha ("proof-of-life: one developer, one environment, one gateway") and the Kubernetes Helm chart is experimental [1]. Latest release v0.0.47 on 2026-05-22, with roughly daily release cadence [2]. License Apache 2.0, Rust 89.6% [1].

**Verdict: reference architecture only, not directly adoptable.** OpenShell sandboxes an _agent_ executing on behalf of a human; the brief's framing is a human typing in a browser-attached shell. The two surfaces are architecturally different. Ideas worth borrowing for a future iteration: declarative YAML policy enforcement, per-binary network egress allow-lists, sandbox-as-Pod with a policy CRD.

Detail: [`references/openshell.md`](references/openshell.md).

## 2. OpenClaw — direct profile

OpenClaw is **a personal AI assistant** by Peter Steinberger [4, 6], rebranded twice (Clawdbot → Moltbot → OpenClaw) following an Anthropic trademark complaint in January 2026 [6]. MIT license, TypeScript+Swift, 374k stars [4]. The primary interface is messaging (WhatsApp, Telegram, Slack, Discord, Signal, iMessage) with optional voice on macOS/iOS/Android [4]. No official Helm chart or Kubernetes operator from upstream [4]. A third-party `openclaw-rocks/openclaw-operator` exists but is not endorsed.

There is **no browser-accessible terminal for human users** in OpenClaw [4]. The Chromium sandbox is for the agent's automation, not for a human's interactive coding. The `exec` tool's `pty: true` flag is for in-process agent shell exec.

**Verdict: unrelated to the framing — discard.** OpenClaw could plausibly run _inside_ a sandbox Pod as the agent that types alongside the human in the ttyd-served shell, but that is the next research topic (what runs inside the Pod), explicitly out of scope per the brief.

Detail: [`references/openclaw.md`](references/openclaw.md).

## 3. Browser TTY tools — comparison

| Project | Last release | Date | Authn out-of-box | Session per tab (default) | Proxy-friendly (Traefik v3) | Idle RAM | Image size | Base OS |
|---|---|---|---|---|---|---|---|---|
| ttyd | v1.7.7 [9] | 2024-03-30 [9] | Basic, auth-header [8, 10] | Implementation-defined; tmux for sharing | Yes [29] | Gap | 6.9 MB compressed (Alpine) [11] | Alpine [11] |
| gotty (sorenisanerd) | v1.7.2 [15] | 2026-05-17 [15] | Basic, TLS server, TLS client cert, random URL, pass-headers [14] | **Yes — new process per connection** [14] | Yes [29] | Gap | ~19 MB compressed (community Alpine) | Alpine (community images) |
| wetty | v2.7.0 [16] | 2023-09-16 [16] | SSH-based (delegates to backend `sshd`) [16] | Yes (each connection = SSH login) | Yes [29] | Gap | Gap (~105 MB per discovery) | Gap (likely Debian) |
| code-server | v4.121.0 [20] | 2026-05-20 [20] | Password, none, oauth2-proxy/Pomerium/Cloudflare Access [22] | **No — single VS Code session shared** | Yes [29] | ≥1 GB stated min [19] | 265.68 MB compressed (linux/amd64) [25] | Debian [25] |

Key observations the table compresses:

- **ttyd is the smallest** — single C binary + libwebsockets, Alpine, 6.9 MB compressed [11]. The wiki documents the `-H X-WEBAUTH-USER` integration for upstream auth proxies and explicitly recommends running on a unix socket when using header pass-through [10].
- **gotty's default is "new process per client"** — the cleanest isolation semantics of the four [14]. But the fork lineage (yudai archive → sorenisanerd fork) is a maintenance risk, and the 2026 release burst follows a long gap [15].
- **wetty is structurally different** — it proxies an SSH session rather than hosting a shell directly [16]. Authentication is whatever the backend `sshd` enforces. Snyk's "inactive" classification [17] combined with v2.7.0 dated 2023-09-16 [16] is the disqualification: a homelab running wetty in 2026 would be pinning itself to a quiet codebase. The wh0 Glitch writeup [18] documents a real attack class but on the platform-deployment shape rather than a WebSocket-protocol-level flaw in upstream wetty.
- **code-server is the heaviest** by an order of magnitude on both image and RAM floor [19, 25], and Coder's own docs warn against multi-user deployments [22]. CVE-2025-47269 (May 2025, CVSS 8.3, session-cookie exfiltration via `/proxy/`) [21] is recent enough to take seriously.
- **Across all four, the Cross-Site WebSocket Hijacking class** [33] is a structural risk that the auth layer (oauth2-proxy, Origin header validation, per-handshake CSRF tokens) must address — it is not a per-tool quirk.

## 4. Kubernetes deployment patterns

### Helm charts

- **CloudTTY** [26, 27] is the closest thing to a purpose-built ttyd-on-Kubernetes Helm chart. Operator pattern with `cloudshell.cloudtty.io/v1alpha1` CRD; each CloudShell pod runs ttyd. Latest chart 0.8.9 (2025-01-27) [27]; the README's quickstart references 0.5.0 [26] — docs-to-reality gap.
- **code-server** ships an in-tree Helm chart at `ci/helm-chart/values.yaml` [23]. Defaults: `persistence.enabled: true`, `10 Gi`, `ReadWriteOnce`, no ingress, `image.tag: 4.121.0` [23]. Install docs only briefly reference Helm [24].
- **gotty and wetty have no upstream Helm chart.** Raw manifests only.

### Multi-tenant via Argo CD ApplicationSet

The brief's "one Pod per operator" maps directly onto Argo CD's **ApplicationSet List generator** [32]. Each list element parameterizes operator name, PVC name, ingress hostname:

```yaml
generators:
  - list:
      elements:
        - operator: alice
          pvc: alice-sandbox
          host: alice-sandbox
template:
  metadata:
    name: 'sandbox-{{.operator}}'
  ...
```

Adding the 13th operator is one line. Per-operator independent sync, rollback, and ingress.

### Persistent home directory

The code-server chart default (`persistence.enabled: true`, 10 Gi, ReadWriteOnce) is a reasonable starting size for any of the four tools' `$HOME` PVC [23]. One pod per operator means ReadWriteOnce is correct — no NFS or Longhorn needed. The `existingClaim` field is the seam for per-operator PVC names parameterized by ApplicationSet [23].

### Ingress + WebSocket

- **Traefik v3 supports WebSocket out of the box** with no special headers or middlewares [29].
- **Tailscale Operator** with `ingressClassName: tailscale` exposes any Service over the tailnet, requires HTTPS+MagicDNS, hostname defaults to `<ingress-name>-<namespace>`, certs lazy-provisioned (first connect may time out) [28]. This satisfies the brief's single-URL requirement directly.
- **nginx-ingress is archived as of 2026-03-24** [30]. Long-standing WebSocket-drop-on-Ingress-reload [31] was closed without resolution as part of archival. Do not adopt.

### Liveness/readiness probes

Sparse on the public web. Best generic answer for any of the four tools: `httpGet /` against the listen port. Tool-specific probe shapes are not documented upstream.

Detail: [`references/k8s-deployment-patterns.md`](references/k8s-deployment-patterns.md).

## 5. Synthesis

The most boring, lowest-blast-radius starting point:

> One **ttyd** Pod per operator, deployed via **Argo CD ApplicationSet**, fronted by the **Tailscale Operator's** Ingress class, with optional **oauth2-proxy** sidecar terminating identity into ttyd's `X-WEBAUTH-USER` header, and a per-operator **ReadWriteOnce 10 Gi PVC** at `$HOME`.

### Design recommendations

1. **Runtime: ttyd, official Alpine image** — smallest blast radius, simplest auth-header integration [8, 10, 11]. [§3]
2. **One Deployment + Service + Ingress + PVC per operator**, packaged in one chart used by Argo CD ApplicationSet List generator [32]. [§4]
3. **ttyd runs on a unix socket, not TCP**; oauth2-proxy sidecar terminates HTTPS, validates identity, injects `X-WEBAUTH-USER` [10]. [§3]
4. **PVC: ReadWriteOnce, 10 Gi, `existingClaim` parameterized per operator** [23]. [§4]
5. **Ingress: Tailscale Operator** (`ingressClassName: tailscale`), MagicDNS hostname per sandbox, automatic Let's Encrypt cert [28]. [§4]
6. **Liveness/readiness: `httpGet /` against the ttyd port**. Tool-specific probe shapes are sparse [§4].
7. **Do not adopt CloudTTY** for the first iteration — read its CRD as inspiration only [26, 27]. [§4]
8. **Do not adopt NVIDIA OpenShell or OpenClaw** as the runtime. [§1, §2]
9. **Do not adopt nginx-ingress** — archived 2026-03-24 [30, 31]. [§4]
10. **Plan for CSWSH threat model** [33] in whatever auth proxy fronts ttyd. [§3]

Detail and reasoning: [`references/synthesis.md`](references/synthesis.md).

## Limitations and gaps

- **Idle-RAM benchmarks missing for all four tools.** No first-party numbers in upstream READMEs; community data too scattered to cite.
- **Wetty's Dockerfile could not be fetched** in-session (404 on `main`); base OS is inferred from the Docker Hub image rather than verified from source.
- **Several CVE claims for OpenShell and OpenClaw** (sourced from secondary tech-press URLs by discovery sub-agents) are flagged in [`citations.md`](citations.md) §"Sources noted but not verified in-session" and are deliberately not cited from the deliverable.
- **Tool-specific liveness/readiness probe shapes** are not documented in upstream repos for ttyd, gotty, or wetty.
- **The recommendation favors operational boring over feature richness.** If the eventual workflow requires VS Code's UI, the synthesis points to code-server as a second iteration with higher RAM floor and CVE history accepted.
- **The "no per-operator identity" defense assumes a homelab with one or two trusted operators.** For a multi-person tailnet, the oauth2-proxy path becomes mandatory rather than optional.
