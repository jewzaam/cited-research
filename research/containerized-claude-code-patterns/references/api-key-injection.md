# Dimension 3 — Anthropic API key injection into a Pod

**What this covers:** Claude Code's supported auth modes, the K8s Secret injection patterns that fit each, rate-limit implications of one key across N concurrent sandbox Pods, per-pod vs shared-key trade-offs, and the **harness-detection billing trap** that converts subscription accounts to pay-as-you-go when containerized Claude Code is detected.

All facts cite [`citations.md`](../citations.md). Date of research: 2026-05-23.

---

## TL;DR

Claude Code supports six auth modes; in a Pod only four are headlessly viable: `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN` (gateway/proxy), `CLAUDE_CODE_OAUTH_TOKEN` (long-lived OAuth from `claude setup-token`), and cloud-provider auth (`CLAUDE_CODE_USE_BEDROCK=1` / `_VERTEX` / `_FOUNDRY`). Interactive `claude login` does not work from containers [4]. The recommended K8s Secret pattern is **file-mount via projected volume** (smaller exposure surface than env var) plus **External Secrets Operator + Stakater Reloader** for rotation [18], but Claude Code does not natively read auth from a file — your entrypoint must export the env var from the file. **Anthropic rate limits are enforced per organization, not per API key** [9], so N concurrent Pods sharing one key contend for one shared bucket and minting more keys does not raise aggregate limits. Cloud-provider auth (Bedrock/Vertex) bypasses Anthropic rate limits entirely but **disables auto mode** [2] — for unattended Pod use, "auto mode" and "cloud-provider auth" are mutually exclusive. The single most important non-obvious risk: **harness detection** ([17] and June 15 2026 dual-bucket billing per [4] and [39a]) — containerized Claude Code is the canonical case that triggers pay-as-you-go billing on subscription accounts.

## 3.1 Auth modes Claude Code supports

The official authentication docs [4] enumerate six methods in precedence order. Items with `[H]` work headlessly inside a Pod; `[I]` requires an interactive browser.

| # | Method | Trigger | Headless? | Notes |
|---|---|---|---|---|
| 1 | Cloud provider | `CLAUDE_CODE_USE_BEDROCK=1` (or `_VERTEX` / `_FOUNDRY`) | [H] | AWS / GCP / Azure credential chain; IRSA in EKS, Workload Identity in GKE |
| 2 | `ANTHROPIC_AUTH_TOKEN` env | Always | [H] | Sent as `Authorization: Bearer`; for LLM gateway/proxy use |
| 3 | `ANTHROPIC_API_KEY` env | Always | [H] | Sent as `X-Api-Key`; in interactive mode prompted once to approve; in `-p` mode always used |
| 4 | `apiKeyHelper` script | Defined in settings | [H] | Returns API key on stdout; refreshes every 5 min or on HTTP 401; `CLAUDE_CODE_API_KEY_HELPER_TTL_MS` configures |
| 5 | `CLAUDE_CODE_OAUTH_TOKEN` env | Always | [H] | One-year OAuth token generated by `claude setup-token`; ties to Pro/Max/Team/Enterprise subscription |
| 6 | Subscription OAuth | `/login` | [I] | Browser-based; needs callback to localhost; **broken in containers** [4] |

### 3.1.1 Why `claude login` doesn't work in a Pod

The verbatim warning from [4]:

> If your browser shows a login code instead of redirecting back after you sign in, paste it into the terminal at the 'Paste code here if prompted' prompt. This happens when the browser can't reach Claude Code's local callback server, which is common in WSL2, SSH sessions, and containers.

For an unattended Pod (CronJob, Job, Deployment with browser TTY operator), the OAuth callback never completes. **Only options 1–5 above are viable.**

### 3.1.2 Precedence gotcha

From [4]: "If you have an active Claude subscription but also have `ANTHROPIC_API_KEY` set in your environment, the API key takes precedence once approved." For a Pod where the operator wants subscription consumption, ensure `ANTHROPIC_API_KEY` is NOT set anywhere in the container env — including from a debug shell. The clean way: use `CLAUDE_CODE_OAUTH_TOKEN` from a pre-generated `claude setup-token` token, and never set `ANTHROPIC_API_KEY`.

But this collides with harness detection — see §3.5.

## 3.2 Kubernetes Secret injection patterns

### 3.2.1 Env-var injection (simplest, weakest)

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: claude-credentials
type: Opaque
stringData:
  ANTHROPIC_API_KEY: "sk-ant-..."
---
apiVersion: apps/v1
kind: Deployment
spec:
  template:
    spec:
      containers:
      - name: claude
        envFrom:
        - secretRef:
            name: claude-credentials
```

Pattern used by [14] (Hnyk CronJob).

**Risks:**
- Env vars appear in `kubectl describe pod` output (visible to any reader of the namespace)
- Env vars appear in `/proc/<pid>/environ` (visible to any process in the same container or as the same user on the host if not user-namespaced)
- Docker layer caching can bake the key into the image if you ever set it as an ARG/ENV at build time (`docker history` reveals)
- Claude Code can read its own env vars and has been observed to disclose them in error messages on confused state [38a]

### 3.2.2 File-mount injection (smaller exposure surface)

```yaml
apiVersion: apps/v1
kind: Deployment
spec:
  template:
    spec:
      containers:
      - name: claude
        volumeMounts:
        - name: claude-secret
          mountPath: /run/secrets/claude
          readOnly: true
        command: ["/bin/bash", "-c"]
        args:
        - |
          export ANTHROPIC_API_KEY="$(cat /run/secrets/claude/api-key)"
          exec claude -p --dangerously-skip-permissions ...
      volumes:
      - name: claude-secret
        secret:
          secretName: claude-credentials
          defaultMode: 0400
          items:
          - key: ANTHROPIC_API_KEY
            path: api-key
```

The file is readable only by the container user, does not appear in `kubectl describe pod`, and does not propagate to subprocess env unless explicitly re-exported. The shell-export step is required because **Claude Code reads from env vars, not from a file path** — there is no `ANTHROPIC_API_KEY_FILE` equivalent documented [4]. An `apiKeyHelper` script reading the same file is the cleanest variant because it re-fetches on 401, supporting in-flight rotation [4].

### 3.2.3 External Secrets Operator + Reloader

For rotation:

1. Store the master key in AWS Secrets Manager / HashiCorp Vault / GCP Secret Manager
2. External Secrets Operator (ESO) syncs to a K8s Secret on a `refreshInterval` (default 1h)
3. Stakater Reloader watches the K8s Secret; on change, annotates the Deployment to trigger a rolling restart [18]

The Reloader annotation [18] verbatim:

```yaml
metadata:
  annotations:
    reloader.stakater.com/auto: "true"
```

For env-var injection this restarts every Pod whose Deployment references the Secret. For file-mount injection a restart is still needed unless the entrypoint re-reads the file on each invocation. **There is no in-process credential refresh path in Claude Code itself** — community feature request #29910 (per counter-discovery) was open and unresolved as of iter-1 collection.

### 3.2.4 Cloud-provider auth (no static Anthropic key)

For EKS Pods, IRSA (IAM Roles for Service Accounts) eliminates the static key entirely [5]:

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: claude-runner
  annotations:
    eks.amazonaws.com/role-arn: arn:aws:iam::ACCOUNT:role/claude-bedrock-role
---
apiVersion: apps/v1
kind: Deployment
spec:
  template:
    spec:
      serviceAccountName: claude-runner
      containers:
      - name: claude
        env:
        - name: CLAUDE_CODE_USE_BEDROCK
          value: "1"
        - name: AWS_REGION
          value: "us-east-1"
```

Required IAM policy (verbatim from [5]):

```json
{
  "Statement": [
    {
      "Sid": "AllowModelAndInferenceProfileAccess",
      "Effect": "Allow",
      "Action": [
        "bedrock:InvokeModel",
        "bedrock:InvokeModelWithResponseStream",
        "bedrock:ListInferenceProfiles",
        "bedrock:GetInferenceProfile"
      ],
      "Resource": [
        "arn:aws:bedrock:*:*:inference-profile/*",
        "arn:aws:bedrock:*:*:application-inference-profile/*",
        "arn:aws:bedrock:*:*:foundation-model/*"
      ]
    },
    {
      "Sid": "AllowMarketplaceSubscription",
      "Effect": "Allow",
      "Action": ["aws-marketplace:ViewSubscriptions","aws-marketplace:Subscribe"],
      "Resource": "*",
      "Condition": {"StringEquals": {"aws:CalledViaLast": "bedrock.amazonaws.com"}}
    }
  ]
}
```

Strict trade-off [2], [5]: **auto mode is NOT available on Bedrock/Vertex/Foundry.** Choosing cloud-provider auth means accepting `--dangerously-skip-permissions` for unattended runs or accepting manual approval prompts.

`/login` and `/logout` are disabled when Bedrock is active [5]. Region must be set via `AWS_REGION` env var — Claude Code does NOT read `~/.aws/config` for region [5].

## 3.3 Rate-limit implications of one shared key across N Pods

**Critical fact:** "Limits are set at the organization level" [9]. All Pods using the same API key under the same Anthropic organization share the same rate-limit bucket.

Per-tier limits for the most-used models [9]:

| Tier | Spend req. | Sonnet 4.x: RPM / ITPM / OTPM | Opus 4.x: RPM / ITPM / OTPM |
|---|---|---|---|
| 1 | $5 | 50 / 30,000 / 8,000 | 50 / 500,000 / 80,000 |
| 2 | $40 | 1,000 / 450,000 / 90,000 | 1,000 / 2,000,000 / 200,000 |
| 3 | $200 | 2,000 / 800,000 / 160,000 | 2,000 / 5,000,000 / 400,000 |
| 4 | $400 | 4,000 / 2,000,000 / 400,000 | 4,000 / 10,000,000 / 800,000 |

(Sonnet 4.x limit is a total across Sonnet 4.6, 4.5, 4. Opus 4.x is a total across Opus 4.7, 4.6, 4.5, 4.1, 4 [9].)

Algorithm: token-bucket, not fixed-window — capacity replenishes continuously [9]. Short bursts above the per-minute rate are possible if tokens have accumulated.

**No explicit concurrent-request cap is published** in the official rate-limits docs [9]. The binding constraint for an N-pod sandbox is whichever of RPM, ITPM, OTPM hits first. A single Claude Code session can consume substantial input per call (system prompt + working-tree context + tool outputs — community estimates 50K–150K input tokens per call, not first-party data). At Tier 1 (30,000 ITPM Sonnet), 1–2 concurrent active sessions can saturate; at Tier 4 (2M ITPM Sonnet), ~10–20 concurrent active sessions become realistic — but this is a calculation against an unverified per-session figure; measure your own.

### 3.3.1 Cache-aware ITPM is a free 5–10× headroom

For most Claude models (all non-Haiku-3.5), `cache_read_input_tokens` do NOT count toward ITPM [9]. With 80% cache hit rate, effective throughput on a 2M ITPM limit is ~10M total input tokens/min. Prompt caching is therefore the single best lever for N-Pod scaling on a shared key — and Claude Code's prompt structure (long system prompt + CLAUDE.md) is well-suited to caching.

### 3.3.2 429 behavior

429 errors return a `retry-after` header [9]. Anthropic also enforces "acceleration limits" — sudden traffic spikes can trigger 429 even below the steady-state limit [9]: "To avoid hitting acceleration limits, ramp up your traffic gradually and maintain consistent usage patterns." For N Pods spinning up in parallel (e.g., a CronJob fan-out), stagger startup or use a backoff init.

## 3.4 Per-pod-instance keys vs shared key

| Dimension | Shared key (one key, N pods) | Per-pod keys (one key per pod) |
|---|---|---|
| Setup effort | Simplest (one Secret) | More keys to provision and store |
| Rate-limit pool | Pooled per org (all pods compete) | **Still pooled per org** (limits are per-org per [9]; minting more keys does NOT raise aggregate limits) |
| Compromise blast radius | All pods exposed if one key leaks | Single-pod blast radius |
| Cost attribution | One bill; no per-pod breakdown without Enterprise Analytics API | Possible via Usage & Cost API grouped by `api_key` |
| Rotation | Single rotation event | N rotation events |
| Abuse detection | Anthropic sees one principal; harder to identify which pod misbehaved | One principal per pod; easier attribution |

**The common misconception this dispels:** minting N keys to "increase rate limit headroom" does NOT work — all N keys under one organization share the same per-org rate limit pool [9]. To get independent rate-limit pools you would need separate Anthropic **workspaces** (organizations), which require separate billing accounts and may not match Anthropic's intended use of the workspace primitive.

Workspaces allow per-workspace **sub-limits** (smaller than the org limit), useful for capping a noisy Pod's share — but they cannot grant a workspace MORE than the org limit [9].

## 3.5 Harness detection and the June 15 2026 dual-bucket billing trap

This is the single non-obvious risk most likely to surprise an operator deploying Claude Code in a Pod.

### 3.5.1 The April 2026 harness-detection incident ([17])

In April 2026, Anthropic shipped server-side logic that scans the Claude Code system prompt's git-status content for keywords associated with third-party harnesses [17]:

> Anthropic pulls git status into Claude Code's system prompt and scans for strings like `hermes.md` and `OpenClaw`.

Detection is purely keyword-based string matching, not behavioral analysis [17]. When triggered, sessions are routed from **subscription billing to pay-as-you-go API billing**.

Documented incident: On Patel, $200/month Claude Max 20x subscription, 86% plan unused and 13% weekly usage — got $200.98 in unexpected charges because a git commit message contained `hermes.md` [17]. Theo Brown reproduced the bug by creating an empty repo with `"OpenClaw"` in a JSON blob [17]. Anthropic (Tariq) publicly apologized: "Sorry, this was a bug with the third-party harness detection and how we pull git status" [17] and offered refunds.

The fix was for false positives. The detection itself remains.

### 3.5.2 The June 15 2026 structural change

The official auth docs [4] include this verbatim warning:

> Starting June 15, 2026, Agent SDK and `claude -p` usage on subscription plans will draw from a new monthly Agent SDK credit, separate from your interactive usage limits. See "Use the Claude Agent SDK with your Claude plan" for details.

Coverage in The Register [39a] and the apiyi.com transition guide [44a] frames this as: programmatic/agentic use of Claude Code on subscription plans gets a separate billing pool with overages charged at full API rates and a $2,000/day overage cap. The $2,000/day cap is an automatic charge authorization, not a safety ceiling.

### 3.5.3 What this means for a Pod with `ANTHROPIC_API_KEY`

If the Pod authenticates with `ANTHROPIC_API_KEY` (the simplest and most common pattern), every token is already billed at pay-as-you-go API rates against the API key's organization. Harness detection is moot here — you're already on API billing. The On Patel incident [17] hit a subscription user; an API-key user does not get worse.

If the Pod authenticates with `CLAUDE_CODE_OAUTH_TOKEN` from `claude setup-token` (subscription consumption), then:

- Pre-June-15-2026: harness detection may trigger pay-as-you-go billing on detection of `hermes.md`/`OpenClaw` in git history [17]
- Post-June-15-2026: `claude -p` (the headless mode used in unattended Pods) draws from a separate monthly Agent SDK credit, with overages at full API rates [4], [44a]

The Pod-builder's choice:

| Auth | Billing | Risk |
|---|---|---|
| `ANTHROPIC_API_KEY` | API rates, predictable | None from harness detection. Standard rate-limit management. |
| `CLAUDE_CODE_OAUTH_TOKEN` (subscription) | Subscription credits, then Agent SDK credit pool (post Jun-15), then $2K/day API overage | Harness-detection false positives [17]. Capped daily exposure but real bill. |
| Cloud-provider auth (Bedrock/Vertex) | AWS/GCP billing, independent of Anthropic rate limits | Loses auto mode [2]. |

For unattended N-pod sandboxes, the cleanest pattern is **separate Anthropic API key per sandbox-instance type** (for cost attribution) with cloud-provider auth (Bedrock/Vertex) for the highest-volume Pods that don't need auto mode. For lower-volume Pods that benefit from auto-mode's classifier safety, use `ANTHROPIC_API_KEY` directly.

## 3.6 Anthropic's own credential safety guidance

The official "API key best practices" article (cited as a candidate in iter 1 but not directly re-fetched in iter 2) and the security docs [3] frame the credential-handling responsibility:

- Credentials are stored on disk at `~/.claude/.credentials.json` (mode 0600) on Linux, in Keychain on macOS, in `%USERPROFILE%\.claude\.credentials.json` on Windows [4]
- Credentials are encrypted in the macOS Keychain; on Linux they are protected by file mode 0600 only [4]
- `apiKeyHelper`, `ANTHROPIC_API_KEY`, and `ANTHROPIC_AUTH_TOKEN` apply to terminal CLI sessions only — Claude Desktop and remote sessions use OAuth exclusively [4]

For a Pod, the Linux 0600 file-mode protection is effectively the only on-disk credential protection — emphasizing the value of NOT persisting credentials inside the Pod's filesystem if avoidable, and using projected Secret volumes (which live on tmpfs, not the container's writable layer).

## 3.7 Gaps and limitations

- **Concurrent-request hard cap:** not published in Anthropic's rate-limits docs [9] for the Messages API. Community sources cite "~15 at Tier 2" but this was not verified against the official source in iter 2. Treat the binding constraint as RPM/ITPM/OTPM, not concurrency, until proven otherwise.
- **`.env` auto-read behavior:** counter-discovery surfaced reports that Claude Code auto-reads `.env` files in the working directory without explicit user disclosure ([38a]). Not directly verified in iter 2 but plausible given the agent's general filesystem access. For a Pod, this means: do NOT mount unrelated `.env` files into the workspace volume.
- **Anthropic-side abuse detection on N concurrent containers:** no public documentation found on whether Anthropic flags accounts using one key across many simultaneous container sessions as abuse. Anecdotally not common, but no first-party statement.
- **Per-pod-instance Bedrock cost attribution:** AWS bills by IAM principal/role; using per-Pod IAM roles via IRSA gives clean cost attribution. Anthropic-side attribution under Bedrock is moot (you don't bill Anthropic).
- **Reloader + projected-Secret restart semantics:** [18] documents Deployment restart on Secret change but does not detail behavior for projected Secret volumes specifically — in practice, projected volume content updates automatically without Pod restart in K8s but Claude Code does not re-read the file, so the restart is still required.
- **`claude setup-token` from inside a container:** not explicitly addressed in [4]. The token must be generated interactively on a workstation (because it requires browser OAuth), then exported as `CLAUDE_CODE_OAUTH_TOKEN` for the Pod — the Pod itself cannot generate the token.
