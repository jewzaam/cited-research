# Dimension 4: GitHub — Activity Surfacing

Generated By: Claude Code (Claude Opus 4.6)

## Research Objective

Research approaches for surfacing GitHub activity that needs the user's attention: PRs waiting for the user's review, PRs the user authored that have new reviews/comments, failing CI checks on user's PRs, issues assigned to or mentioning the user, stale PRs (no activity for N days), and release or deployment events.

## 1. GitHub REST API — Notifications

### Endpoint

`GET /notifications` — Lists all notifications for the authenticated user, sorted by most recently updated.

### Query Parameters

| Parameter | Type | Description |
|-----------|------|-------------|
| `all` | boolean | If `true`, show read notifications too |
| `participating` | boolean | If `true`, only show threads where user is directly involved or @mentioned |
| `since` | ISO 8601 | Only show notifications updated after this time |

### Response Fields

Each notification includes: `id`, `repository`, `subject` (with `title`, `url`, `type`), `reason`, `unread`, `updated_at`, `last_read_at`.

### The `reason` Field

The `reason` indicates why the user received the notification. It is modified per-thread and can change if a later notification has a different reason. Values include: `assign`, `author`, `comment`, `invitation`, `manual`, `mention`, `review_requested`, `security_alert`, `state_change`, `subscribed`, `team_mention`.

### Limitations

- **No server-side filter by `reason`** — must fetch all notifications and filter client-side to isolate review requests from mentions from assignments
- **Does not work with** GitHub App user access tokens, GitHub App installation access tokens, or fine-grained personal access tokens. Requires a classic personal access token (PAT) with the `notifications` scope.
- **No digest/summary endpoint** — only raw notification list

- **Source URL:** https://docs.github.com/en/rest/activity/notifications (accessed 2026-03-26)
- **Quality note:** Official GitHub documentation. The authentication limitation is significant — fine-grained PATs cannot access notifications, which conflicts with GitHub's own push toward fine-grained tokens.

### Additional Notification Management Endpoints

- `PUT /notifications` — Mark all notifications as read
- `GET /notifications/threads/{thread_id}` — Get thread details
- `PUT /repos/{owner}/{repo}/notifications` — Mark repo notifications as read
- `GET /repos/{owner}/{repo}/subscription` — Check/manage repo subscription

- **Source URL:** https://docs.github.com/en/rest/activity/watching (accessed 2026-03-26)

## 2. GitHub GraphQL API — Targeted Queries

The GraphQL API enables more efficient queries by fetching exactly the data needed in a single request.

### PRs Awaiting User's Review

```graphql
{
  search(query: "type:pr state:open review-requested:USERNAME", type: ISSUE, first: 100) {
    issueCount
    edges {
      node {
        ... on PullRequest {
          url
          title
          createdAt
          updatedAt
          author { login }
          repository { nameWithOwner }
        }
      }
    }
  }
}
```

For team review requests: `team-review-requested:ORG/TEAMNAME`

- **Source URL:** https://gist.github.com/MichaelCurrin/f8a7a11451ce4ec055d41000c915b595 (accessed 2026-03-26)
- **Source URL:** https://docs.github.com/en/graphql/reference/queries (accessed 2026-03-26)

### Key Search Qualifiers for GraphQL `search` Query

| Qualifier | Purpose |
|-----------|---------|
| `review-requested:USERNAME` | PRs where user's review is requested |
| `team-review-requested:ORG/TEAM` | PRs where team's review is requested |
| `author:USERNAME` | PRs/issues authored by user |
| `assignee:USERNAME` | Issues/PRs assigned to user |
| `mentions:USERNAME` | Issues/PRs that mention user |
| `commenter:USERNAME` | Issues/PRs where user commented |
| `involves:USERNAME` | Issues/PRs where user is involved (author, assignee, mentioned, or commenter) |
| `is:pr` / `is:issue` | Filter by type |
| `state:open` / `state:closed` | Filter by state |

- **Source URL:** https://docs.github.com/en/graphql/reference/queries (accessed 2026-03-26)

### Batch Query for Multiple Notification Types

GraphQL aliases allow combining multiple search queries in one request:

```graphql
{
  reviewRequested: search(query: "type:pr state:open review-requested:USERNAME", type: ISSUE, first: 50) {
    issueCount
    edges { node { ... on PullRequest { url title updatedAt } } }
  }
  authored: search(query: "type:pr state:open author:USERNAME", type: ISSUE, first: 50) {
    issueCount
    edges { node { ... on PullRequest { url title updatedAt } } }
  }
  assignedIssues: search(query: "type:issue state:open assignee:USERNAME", type: ISSUE, first: 50) {
    issueCount
    edges { node { ... on Issue { url title updatedAt } } }
  }
  mentioned: search(query: "state:open mentions:USERNAME", type: ISSUE, first: 50) {
    issueCount
    edges { node { ... on Issue { url title } ... on PullRequest { url title } } }
  }
}
```

- **Source URL:** https://gist.github.com/StevenACoffman/ffcc754f7f84a69efcb84442eca302e0 (accessed 2026-03-26)
- **Quality note:** GitHub gist with community-contributed snippets. The batch query pattern is sound but must account for the GitHub App token caveat below.

### Caveat: GitHub App Token Restrictions

For GitHub App requests made with user access tokens, you must use separate queries for issues and pull requests (use `is:issue` or `is:pull-request` filters). A combined query returns an empty set of nodes.

- **Source URL:** https://docs.github.com/en/graphql/reference/queries (accessed 2026-03-26)

### Rate Limits

- REST API: 5,000 requests per hour for authenticated users
- GraphQL API: 5,000 points per hour. Each query costs at least 1 point; cost increases with complexity. A single GraphQL query can replace many REST calls but costs more points per query.

## 3. CI/CD Status Detection

### Querying CI Status via GraphQL

There are two distinct systems for CI status on GitHub:

1. **Commit Statuses** (legacy): The `status` field on a commit, with `state` and `contexts`
2. **Check Runs** (newer, GitHub Actions): The `checkSuites` and `checkRuns` connections on a commit

A comprehensive query combines both:

```graphql
query($owner: String!, $repo: String!, $pull_number: Int!) {
  repository(owner: $owner, name: $repo) {
    pullRequest(number: $pull_number) {
      commits(last: 1) {
        nodes {
          commit {
            statusCheckRollup {
              state
            }
            checkSuites(first: 100) {
              nodes {
                checkRuns(first: 100) {
                  nodes {
                    name
                    conclusion
                    status
                    permalink
                  }
                }
              }
            }
          }
        }
      }
    }
  }
}
```

The `statusCheckRollup.state` provides a single aggregate: `SUCCESS`, `FAILURE`, `PENDING`, or `ERROR`.

- **Source URL:** https://dev.to/gr2m/github-api-how-to-retrieve-the-combined-pull-request-status-from-commit-statuses-check-runs-and-github-action-results-2cen (accessed 2026-03-26)
- **Source URL:** https://github.com/orgs/community/discussions/24508 (accessed 2026-03-26)
- **Quality note:** The DEV Community article by gr2m (a well-known GitHub ecosystem developer) is thorough and explains the dual-system complexity clearly. Some CI tools use commit statuses, some use check runs, and some use both — a PA must query both to get the full picture.

### Limitation: No Bulk CI Status Query

There is no single API call to get "all my PRs with failing CI." The PA must:
1. Query PRs authored by the user (`author:USERNAME`)
2. For each PR, query the head commit's `statusCheckRollup`

This is an N+1 query problem. GraphQL can mitigate it by embedding `statusCheckRollup` in the PR search query, but pagination limits still apply.

## 4. GitHub CLI (`gh`) Capabilities

### `gh pr status`

Displays relevant PRs in three sections:
1. Current branch PR
2. PRs created by you
3. PRs requesting a code review from you

Each shows check status and review state. Supports `--json` output with fields including `assignees`, `author`, `reviewRequests`, `reviewDecision`, `reviews`, `state`, `updatedAt`, `statusCheckRollup`.

- **Source URL:** https://cli.github.com/manual/gh_pr_status (accessed 2026-03-26)

### `gh search prs`

Search for PRs across repos:
```bash
gh search prs --review-requested=@me --state=open
gh search prs --author=@me --state=open
```

**Limitation:** The `--json` output for `gh search prs` does not support `reviewRequests` as a field, limiting automation capabilities.

- **Source URL:** https://github.com/cli/cli/discussions/6801 (accessed 2026-03-26)

### Known Bug: Review Re-Requested Shows as Approved

`gh pr status` may incorrectly show a PR as "Approved" when a review has been re-requested. `gh pr view` correctly shows "(Requested)" status.

- **Source URL:** https://github.com/cli/cli/issues/1610 (accessed 2026-03-26)

### `gh api` for Direct API Access

The `gh` CLI can make arbitrary API calls:
```bash
gh api /notifications --jq '.[] | select(.reason == "review_requested")'
gh api graphql -f query='{ search(query: "type:pr state:open review-requested:@me", type: ISSUE, first: 50) { issueCount } }'
```

This provides full API access with built-in authentication.

### `gh-pr-review` Extension

A community extension adding inline PR review comment support. Commands include listing comments, replying, starting/submitting pending reviews, and resolving threads from the terminal.

- **Source URL:** https://github.com/agynio/gh-pr-review (accessed 2026-03-26)
- **Quality note:** Community extension, not official GitHub. Actively developed as of 2025. Designed to be "LLM-ready and ideal for automated PR review agents."

## 5. GitHub MCP Server

### Official GitHub MCP Server

GitHub maintains an official MCP server (`github/github-mcp-server`) providing tool access organized into toolsets.

### Default Toolsets: `repos`, `issues`, `pull_requests`

### Available Toolsets (opt-in): `actions`, `code_security`, `secret_protection`, `notifications`, `experiments`

### Key Tools for PA Use Cases

**Notifications toolset:**
- `list_notifications` — Lists all GitHub notifications for the authenticated user, including unread notifications, mentions, review requests, assignments, and updates. Supports filtering by `participating`, `since` (ISO 8601), and pagination (`page`, `perPage` up to 100).
- `get_notification_details` — Detailed info for a specific notification thread.
- `manage_notification_subscription` — Ignore, watch, or delete a notification thread subscription.
- `mark_all_notifications_read` — Mark all as read.

**Pull requests toolset:**
- `list_pull_requests` — List PRs in a repository.
- `get_pull_request` — Get details of a specific PR.
- `get_pull_request_status` — Get status of head commit (CI status).
- `get_pull_request_files` — Get changed files.
- `get_pull_request_review_comments` — Get review comments.
- `pull_request_review_write` — Create/submit/delete reviews.

**Issues toolset:**
- `create_issue`, `get_issue`, `get_issue_comments`, `add_issue_comment`, `list_sub_issues`

**Actions toolset:**
- `actions_get` — Get details of workflows, workflow runs, jobs, and artifacts. Methods include `get_workflow`, `get_workflow_run`, `get_workflow_run_usage`, `get_workflow_run_logs_url`, `download_workflow_run_artifact`, `get_workflow_job`.

### Deployment Options

- **Remote:** Hosted by GitHub (easiest setup)
- **Local:** Self-hosted via Docker or binary

### Configuration

- `--toolsets` flag or `GITHUB_TOOLSETS` environment variable
- Read-only mode available (`--read-only`)
- Dynamic toolset discovery available for AI hosts

- **Source URL:** https://github.com/github/github-mcp-server (accessed 2026-03-26)
- **Source URL:** https://docs.github.com/en/copilot/how-tos/provide-context/use-mcp/use-the-github-mcp-server (accessed 2026-03-26)
- **Source URL:** https://github.blog/changelog/2025-10-29-github-mcp-server-now-comes-with-server-instructions-better-tools-and-more/ (accessed 2026-03-26)
- **Quality note:** Official GitHub product. The October 2025 changelog entry indicates active development with tool consolidation (merging related tools into unified multifunctional ones). Tool names and signatures may change.

## 6. GitHub Actions for Notification/Digest Workflows

### Scheduled Digests

GitHub Actions supports `schedule` triggers with cron syntax. A daily digest workflow could:
1. Run at a fixed time (e.g., 8 AM)
2. Query the GitHub API for PRs needing review, authored PRs with new activity, failing CI
3. Format results as a message
4. Post to Slack via webhook or send email

**Limitation:** GitHub Actions notifications are sent only to the user who last modified the workflow's cron syntax. There is no native way to notify a team about failed scheduled workflows.

- **Source URL:** https://docs.github.com/en/actions/concepts/workflows-and-actions/notifications-for-workflow-runs (accessed 2026-03-26)
- **Source URL:** https://docs.github.com/en/subscriptions-and-notifications/how-tos/managing-github-actions-notifications (accessed 2026-03-26)

### `actions/stale` for PR/Issue Staleness

The official `actions/stale` action marks issues and PRs that have not had recent interaction:
- Configurable idle period before marking as stale
- Configurable period after stale before auto-closing
- Exemption by label (e.g., `work-in-progress`)
- Runs on a scheduled cron trigger

```yaml
- uses: actions/stale@v9
  with:
    stale-pr-message: 'This PR has been inactive for 14 days.'
    days-before-pr-stale: 14
    days-before-pr-close: 7
    exempt-pr-labels: 'work-in-progress,awaiting-approval'
```

- **Source URL:** https://github.com/actions/stale (accessed 2026-03-26)
- **Quality note:** Official GitHub action. Well-maintained. Addresses the stale PR detection use case natively within repositories, but operates per-repo — not a cross-repo personal digest.

## 7. Third-Party Tools for GitHub Activity Aggregation

### Gitmore

AI-powered GitHub activity digest and notification reports. Connects via OAuth, receives commit and PR event metadata through webhooks, uses AI to generate human-readable activity digests. Delivery via Slack or email on configurable schedules (daily, weekly, custom).

- **Source URL:** https://gitmore.io/git-reporting/tool/github (accessed 2026-03-26)
- **Source URL:** https://gitmore.io/blog/github-activity-digest-notification-tools (accessed 2026-03-26)
- **Quality note:** Commercial product. The blog post on their site lists competitor tools, providing useful landscape context, but is inherently promotional.

### GitDailies

GitHub App that sends daily summaries to help engineers stay up to date. Delivers notifications via Email, Slack, or Telegram. Designed for daily standup context.

- **Source URL:** https://gitmore.io/blog/github-activity-digest-notification-tools (accessed 2026-03-26) (listed in Gitmore's competitor analysis)

### Axolo

GitHub Slack bot focused on PR review flow. Sends daily notifications only if a PR was not recently reviewed. Provides instant feedback, automates daily PR reminders, and centralizes communication.

- **Source URL:** https://axolo.co/ (accessed 2026-03-26)

### Swarmia

Team-level daily digest showing PRs, issues, and working agreements requiring action. Configurable content (PRs in review, in progress, merged). Highlights PRs waiting for review and ready to merge separately.

- **Source URL:** https://help.swarmia.com/notifications/team-notifications (accessed 2026-03-26)

### GitHub Scheduled Reminders (Built-in)

GitHub supports configuring email reminders for overdue reviews via organization settings, though capabilities are limited compared to third-party tools.

- **Source URL:** https://graphite.com/guides/configure-github-email-reminders-for-overdue-reviews (accessed 2026-03-26)
- **Quality note:** The Graphite guide describes GitHub's built-in feature but also promotes Graphite's own notification system. The built-in reminder is organization-level, not personal.

## 8. Recommended PA Architecture for GitHub Monitoring

Based on the research, a PA surfacing GitHub activity would use:

1. **GraphQL batch queries** (primary): A single query combining multiple `search` calls with aliases to detect:
   - PRs awaiting review (`review-requested:USERNAME`)
   - Authored PRs with activity (`author:USERNAME` then check `updatedAt`)
   - Assigned issues (`assignee:USERNAME`)
   - Mentions (`mentions:USERNAME`)

2. **CI status embedding**: Include `statusCheckRollup` in PR queries to detect failing CI without separate calls.

3. **Notifications API** (supplementary): `GET /notifications?participating=true` for real-time thread-level awareness of comments, mentions, and review requests. Requires classic PAT.

4. **GitHub MCP Server** (for AI-native integration): The `list_notifications` and PR tools provide a structured interface for AI agents. The `notifications` toolset must be explicitly enabled.

5. **`gh` CLI** (for scripts/automation): `gh pr status` provides a quick personal dashboard; `gh api` enables arbitrary API access with built-in auth.

### Gaps Identified

- **No personal activity digest API** — GitHub has no endpoint that returns "here's what needs your attention today." This must be assembled from multiple queries.
- **No server-side reason filter on notifications** — cannot query "only review requests" without fetching all notifications and filtering client-side
- **Fine-grained PAT incompatibility** — the notifications API requires classic PATs, conflicting with GitHub's push toward fine-grained tokens
- **Cross-repo aggregation** — all search queries are global (which is good), but `actions/stale` and CI monitoring are per-repo
- **No webhook API for personal events** — GitHub webhooks are per-repository or per-organization, not per-user. There is no "notify me when any repo I care about has activity" webhook.
- **Review re-request detection** — `gh pr status` has a known bug showing re-requested reviews as "Approved"
