# AI-Assisted Development Security Analysis

Generated By: Claude Code (Claude Opus 4.6)
Research Date: 2026-03-27

## TL;DR

AI coding assistants introduce security risks across five surfaces: **dependencies** (877K+ malicious packages in the wild, plus LLM-hallucinated package names), **generated code** (1.7-2.74x more vulnerable than human code), **generated tests** (100% coverage can coexist with 4% mutation score), **external resources** (prompt injection remains unsolved — all defenses bypassed >90%), and **permission gaps** (hook-based security defeated by regex evasion, TOCTOU, command encapsulation, and exfiltration through allowed channels).

**Command encapsulation bypass** is particularly insidious: PreToolUse hooks only inspect the command Claude runs, not commands spawned internally [EB-1]. `make test` is allowlisted, but the Makefile can run `pip install` without the hook seeing it. NVIDIA's AI Red Team documents this as a known attack pattern [EB-3]. Claude Code's OS sandbox mitigates this when enabled, but sandbox is opt-in [EB-2].

The single most impactful action: **write PreToolUse hooks for dependency scanning + PostToolUse hooks for lockfile diffing** — together they cover both direct installs and encapsulated installs.

## Key Decision Table

| Risk | Current Defense | Gap | Recommended Action | Effort |
|------|----------------|-----|-------------------|--------|

| Encapsulated dependency installs | None | **Critical** | PostToolUse lockfile diff (catches `make`/`npm run` hiding installs) | Low |
| AI code vulnerabilities | security-guidance plugin (9 patterns) | High | PostToolUse SAST feedback loop (Semgrep/Bandit) | Medium |

| MCP server supply chain | Trust on first use | High | Docker isolation + server audit | Low |

| Config file weaponization | Not in block_paths.py | Medium | Add .claude/settings.json, .mcp.json to blocked paths | Low |
| Regex evasion of hooks | Regex-based blocking | Medium | Shell parser normalization + PostToolUse verification | Medium |
| Prompt injection | Haiku pre-filter + sandbox | **Unsolvable** | Defense-in-depth, accept residual risk | N/A |

## Quick Decision Framework

1. **Is it a dependency?** → Run through scanning hook before installing (Priority 1)
1b. **Did a Makefile/script just run?** → Diff lockfiles to catch encapsulated installs (Priority 1b)
2. **Is it generated code?** → Run SAST, feed results back to LLM (Priority 2)
3. **Is it a generated test?** → Run mutation testing to verify it catches real bugs (Priority 3)
4. **Is it an MCP server?** → Run in Docker, audit tool descriptions (Priority 4)
5. **Is it from a cloned repo?** → Block config file writes from that repo (Priority 6)

## Why PreToolUse Hooks, Not Skills

| Property | PreToolUse Hooks | Skills |
|----------|-----------------|--------|
| Triggering | Deterministic (matcher pattern) | Probabilistic (LLM description matching) |
| Bypass resistance | Cannot be bypassed by prompt injection | LLM can be manipulated to skip |
| Can block actions | Yes (exit code 2) | No |
| Fires on sub-agents | Yes | Unreliable |
| Community observation | Reliable | "Often ignores available skills entirely" |
