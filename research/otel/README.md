# Python Logging + OpenTelemetry on OpenShift

> **Generated By: Claude Code (Claude Opus 4.6)**

Research into how Python's `logging` module interacts with OpenTelemetry, what export
options exist, and whether OTEL is a good fit for a Python app on OpenShift shipping
logs to the OpenShift logging stack (Logging Operator).

## TL;DR

Python's `logging` module integrates with OTEL via a **bridge pattern** — you keep
existing logging code and attach an OTEL handler that converts log records into the
OTEL data model. You do **not** have to ship to an OTEL Collector; you can export
directly to any OTLP-compatible backend, or even to stdout (for debugging). However,
the OTEL project recommends using a Collector for production.

For your OpenShift scenario, there are two viable paths:

| | Stdout + Logging Operator | OTLP + OTEL Collector |
|---|---|---|
| **Maturity** | GA | OTLP output is Tech Preview |
| **Operators needed** | Logging Operator only | + OTEL Operator + Loki Operator + COO |
| **Trace correlation** | Manual (format strings) | Automatic |
| **Data fidelity** | Lossy (JSON parsing) | Full OTEL data model |
| **Red Hat direction** | Legacy (ViaQ) | Strategic (OTLP-native) |

## Quick Decision Framework

1. **Need production logging today?** → Use structured JSON to stdout with
   `OTEL_PYTHON_LOG_CORRELATION=true` for trace context. The Logging Operator
   collects it via Vector. All GA components.

2. **Also need traces and metrics via OTEL?** → Deploy the OTEL Collector (DaemonSet)
   via the Red Hat OTEL Operator. Ship logs via OTLP alongside traces/metrics for
   unified observability. Accept that OTLP log forwarding is Tech Preview.

3. **Want the future-proof path?** → Plan for OTLP. Red Hat is making OpenShift an
   "OTLP-native platform" and LokiStack's default data model will switch from ViaQ
   to OpenTelemetry.

4. **Migrating incrementally?** → Hybrid: stdout for the Logging Operator + OTLP to
   the OTEL Collector. Run both pipelines during transition.
