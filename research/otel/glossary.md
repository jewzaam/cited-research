# Glossary

> Generated By: Claude Code (Claude Opus 4.6)

Terms used throughout this research. Citations reference [citations.md](citations.md).

---

## Bridge API

The OTEL Logs API. Unlike the Traces and Metrics APIs (which application developers
call directly), the Logs API is a bridge — it connects existing logging libraries
(Python's `logging`, Java's Log4j, etc.) to the OTEL pipeline without requiring
code changes [1].

## CLF — ClusterLogForwarder

The OpenShift CRD that configures log routing. Defines inputs (sources), filters,
pipelines, and outputs (destinations). In Logging 6.x, the API group is
`observability.openshift.io` [18]. Manages Vector under the hood.

## CLO — Cluster Logging Operator

The OpenShift operator that manages log collection infrastructure. Does not collect
logs itself — it configures and manages Vector (the collector) [16].

## ConsoleLogRecordExporter

The OTEL Python SDK's stdout exporter. Outputs log records to the console in a
human-readable but **unstandardized** format. For debugging and learning only — not
production [7].

## COO — Cluster Observability Operator

Required alongside the Logging Operator and Loki Operator when configuring OTLP
ingestion into LokiStack [21].

## DaemonSet (Collector)

Deployment mode where one OTEL Collector pod runs per node. Used for node-level
telemetry collection (Filelog Receiver, host metrics). More resource-efficient than
sidecar but has a larger blast radius [26][34]. 50% of Kubernetes OTEL users use
this mode [36].

## Filelog Receiver

An OTEL Collector component that tails and parses log files. In Kubernetes, it
reads from `/var/log/pods/*/*/*.log` [32]. Reached GA in the Red Hat build [24].
Used in DaemonSet mode to collect container stdout/stderr logs without requiring
applications to export OTLP.

## k8sattributesprocessor

An OTEL Collector component that enriches telemetry with Kubernetes pod metadata
(pod name, namespace, deployment, etc.). Ensures consistent attribute names across
logs, traces, and metrics, enabling cross-signal correlation [32].

## LoggingHandler

The Python `logging.Handler` subclass that bridges Python's `logging` module into
the OTEL pipeline. Attach it to a logger, and all `logging.info(...)` calls are
converted to OTEL LogRecords [2]. As of SDK 1.40.0, provided by the
`opentelemetry-instrumentation-logging` contrib package [4][5].

## LokiStack

A Loki deployment managed by the Loki Operator on OpenShift. Serves as the log
storage backend. Supports OTLP ingestion via `lokiStack.dataModel: Otel` [22].
Default data model is currently ViaQ but will change to OpenTelemetry in future
releases [22].

## OTEL — OpenTelemetry

The CNCF project providing vendor-neutral APIs, SDKs, and tools for observability
(logs, traces, metrics). Defines a data model, a protocol (OTLP), and a Collector
for processing and forwarding telemetry.

## OTLP — OpenTelemetry Protocol

The wire protocol for transmitting telemetry data (logs, traces, metrics) between
OpenTelemetry-aware components. OTLP defines how data is serialized and transported,
not what the data contains (that's the OTEL data model).

Three wire formats [13]:

| Format | Transport | Default Port |
|---|---|---|
| `grpc` | Protobuf over gRPC (HTTP/2) | 4317 |
| `http/protobuf` | Protobuf over HTTP | 4318 |
| `http/json` | JSON over HTTP | 4318 |

OTLP is designed to emit data **without loss of information** from the OTEL data
model [8] — unlike writing JSON to stdout, where the receiving collector must parse
and reconstruct structure [30].

In the OpenShift context, OTLP is the convergence point between the Logging Operator
(Vector can output OTLP, currently Tech Preview [19]) and the OTEL Collector (receives
OTLP natively). LokiStack can ingest OTLP directly when configured with
`lokiStack.dataModel: Otel` [22].

## Sidecar (Collector)

Deployment mode where one OTEL Collector pod runs per application pod. Better fault
isolation and gRPC load balancing than DaemonSet, but higher resource cost. Triggered
by annotation `sidecar.opentelemetry.io/inject: "true"` [24]. 23% of Kubernetes OTEL
users use this mode [36].

## Technology Preview

Red Hat's designation for features not yet covered by production SLAs. OTLP output
from the ClusterLogForwarder is Technology Preview across Logging 6.1–6.4 [19][21].
Requires the annotation `observability.openshift.io/tech-preview-otlp-output: "enabled"`.

## Vector

The log collector used by the OpenShift Logging Operator. Runs as a DaemonSet,
one pod per node. Replaced Fluentd (deprecated in 5.6, removed in 6.0) [18].
Reads container logs from `/var/log/containers` [17].

## ViaQ

The legacy data model used by the OpenShift logging stack. Being superseded by the
OpenTelemetry data model [21][22]. Currently the default for LokiStack but will
change in future releases [22].
