## 1. How Python Logging Integrates with OpenTelemetry

### The Bridge Pattern

OpenTelemetry does not replace Python's `logging` module — it bridges it. The OTEL
Logs API is a **bridge API** that connects existing logging libraries to the OTEL
data model [1]:

> "There is a logs bridge API; however, it is different from the Traces and Metrics API,
> because it's not used by application developers to create logs." [1]

In practice, this means:
- You keep all existing `logging.getLogger(__name__).info(...)` calls unchanged
- You attach an OTEL `LoggingHandler` to Python's logger hierarchy
- The handler converts Python `LogRecord` objects into OTEL `LogRecord` objects
- Those OTEL LogRecords flow through the SDK pipeline (processors → exporters)

### Setup

```python
import logging
from opentelemetry.sdk._logs import LoggerProvider, LoggingHandler
from opentelemetry.sdk._logs.export import BatchLogRecordProcessor
from opentelemetry.exporter.otlp.proto.grpc._log_exporter import OTLPLogExporter
from opentelemetry._logs import set_logger_provider

provider = LoggerProvider()
provider.add_log_record_processor(
    BatchLogRecordProcessor(OTLPLogExporter())
)
set_logger_provider(provider)

handler = LoggingHandler(level=logging.INFO, logger_provider=provider)
logging.getLogger().addHandler(handler)
```
[2]

As of SDK 1.40.0, the `opentelemetry-instrumentation-logging` contrib package provides
auto-instrumentation that installs the handler automatically [4][5].

### Log-Trace Correlation

Two mechanisms exist for correlating logs with traces:

**1. Native OTEL correlation (automatic):** The SDK appends TraceID and SpanID of the
current active Span to every OTEL LogRecord. This happens automatically when logs are
emitted within an active span context [4].

**2. Format-string injection (for stdout/text logs):** Setting
`OTEL_PYTHON_LOG_CORRELATION=true` registers a custom log record factory that adds
`otelTraceID`, `otelSpanID`, `otelServiceName`, and `otelTraceSampled` to Python
LogRecords, making them available in format strings [5]:

```
%(asctime)s %(levelname)s [trace_id=%(otelTraceID)s span_id=%(otelSpanID)s] - %(message)s
```

### Required Packages

| Package | Purpose |
|---|---|
| `opentelemetry-api` | Core API, `set_logger_provider` |
| `opentelemetry-sdk` | `LoggerProvider`, processors, console exporter |
| `opentelemetry-instrumentation-logging` | Auto-instrumentation handler |
| `opentelemetry-exporter-otlp-proto-grpc` | gRPC OTLP exporter (port 4317) |
| `opentelemetry-exporter-otlp-proto-http` | HTTP OTLP exporter (port 4318) |

## 2. Export Options: Where Can OTEL Data Go?

### Can it go to stdout?

**Yes**, via `ConsoleLogRecordExporter` — but this is for **debugging only** [7]:

> "This exporter is intended for debugging and learning purposes. It is not recommended
> for production use. The output format is not standardized and can change at any time." [7]

The output is human-readable but not machine-parseable in a stable way.

For production stdout use, the practical approach is to use Python's standard logging
with `OTEL_PYTHON_LOG_CORRELATION=true` to inject trace context, and configure a JSON
formatter to write structured JSON to stdout [5][31].

### Do you have to ship to an OTEL Collector?

**No.** You have three options:

| Option | How | Production-Ready? |
|---|---|---|
| Direct to backend | Point `OTLPLogExporter` at backend's OTLP endpoint | Yes, if backend supports OTLP |
| Via OTEL Collector | Ship OTLP to a Collector, which forwards onward | Yes (recommended) [38] |
| Console/stdout | `ConsoleLogRecordExporter` | No (debugging only) [7] |

> "The most direct deployment pattern doesn't use a Collector at all. In this approach,
> applications instrumented with an OpenTelemetry SDK export telemetry signals straight
> to a backend." [12]

However, the OTEL project recommends using a Collector [38]:

> "It is a best practice to send telemetry from containers to an OpenTelemetry Collector
> instead of directly to a backend. The Collector helps simplify secret management,
> decouples data export problems from your apps, and lets you add additional data to
> your telemetry." [38]

### OTLP Exporters

| Exporter | Port | Protocol | Path |
|---|---|---|---|
| gRPC (`opentelemetry-exporter-otlp-proto-grpc`) | 4317 | `grpc` | None |
| HTTP (`opentelemetry-exporter-otlp-proto-http`) | 4318 | `http/protobuf` | `/v1/logs` |

Both are configured via environment variables (`OTEL_EXPORTER_OTLP_ENDPOINT`, etc.) [13].

See [reference/export-options.md](reference/export-options.md) for the full env var table.

## 3. OpenShift Logging Stack: How It Works

### Current Architecture

The OpenShift Logging Operator (Cluster Logging Operator) manages log collection via
**Vector** running as a DaemonSet — one pod per node [17][18]:

- Fluentd was deprecated in Logging 5.6 and **removed in Logging 6.0** [18]
- Vector reads container logs from `/var/log/containers` [17]
- Three log categories: application, infrastructure, audit [17]

### What Format Does It Expect?

The logging stack collects **whatever containers write to stdout/stderr** — plain text
or JSON [39]. JSON parsing is opt-in via `parse: json` in the ClusterLogForwarder [39].

### Supported Backends

The ClusterLogForwarder supports: azureMonitor, cloudwatch, elasticsearch,
googleCloudLogging, http, kafka, loki, lokistack, **otlp**, splunk, syslog [19].

### OTLP Support Status

OTLP output from the ClusterLogForwarder is **Technology Preview** (not GA) across
Logging 6.1–6.4 [19][21]. It requires an explicit annotation and uses the OpenTelemetry
data model instead of ViaQ [21].

LokiStack can ingest OTLP data via `lokiStack.dataModel: Otel`, but this requires
three operators: Logging + Loki + Cluster Observability Operator [21][22].

See [reference/openshift-logging.md](reference/openshift-logging.md) for full details.

## 4. OTEL Collector on OpenShift

Red Hat provides the "Red Hat build of OpenTelemetry" operator, which deploys Collector
instances via the `OpenTelemetryCollector` CRD [24].

### Deployment Modes

| Mode | When to Use |
|---|---|
| DaemonSet | Node-level collection (Filelog Receiver, host metrics) [26] |
| Sidecar | Per-pod collection, in-container file access [26] |
| Deployment | Gateway/aggregation layer |

DaemonSet is by far the most common (50% vs 23% sidecar in 2026 survey) [36].

### Key Trade-off: DaemonSet vs Sidecar

DaemonSet is more resource-efficient but has a larger blast radius. Sidecar provides
better fault isolation and gRPC load balancing but costs more resources and is expensive
with k8sattributesprocessor at scale [34].

### Forwarding to LokiStack

The OTEL Collector can forward logs directly to a LokiStack instance via its OTLP
endpoint [27]. LokiStack in `openshift-logging` mode automatically maps OTLP attributes
to Loki stream labels [20].

See [reference/collector-architecture.md](reference/collector-architecture.md) for full details.

## 5. Is OTEL a Good Fit? Analysis

### Your Scenario
- Python app deployed in pods on OpenShift
- Planning to ship logs to the OpenShift logging stack (Logging Operator)
- Want to understand OTEL's role

### Three Architecture Options

#### Option A: Structured JSON to Stdout + Logging Operator

```
Python App → structured JSON (stdout) → Vector (Logging Op) → LokiStack
```

- Use `OTEL_PYTHON_LOG_CORRELATION=true` for trace context in log records [5]
- Configure a JSON formatter on the Python logger
- Vector collects from `/var/log/containers` [17]
- ClusterLogForwarder with `parse: json` [39]

**Verdict:** Works today, GA, no extra operators. But trace context requires manual
formatting, and the JSON parse → forward pipeline loses OTEL data model fidelity [30].

#### Option B: OTLP to OTEL Collector → LokiStack

```
Python App → OTLP → OTEL Collector (DaemonSet) → LokiStack OTLP endpoint
```

- Python app uses `OTLPLogExporter` [9][10]
- OTEL Collector with k8sattributesprocessor [32]
- Collector forwards to LokiStack [27]

**Verdict:** Full OTEL data model, automatic trace correlation, unified pipeline for
logs+traces+metrics. But requires additional operators, and the OTLP path through the
logging stack is still Technology Preview [19][21].

#### Option C: Hybrid

Both stdout (for Logging Operator) and OTLP (for OTEL pipeline) simultaneously.
Use during migration or when both consumers exist.

### Recommendation Matrix

| Factor | Option A (Stdout) | Option B (OTLP) |
|---|---|---|
| Works today (GA) | Yes | Partially (OTLP output is Tech Preview) |
| Operator complexity | Low (Logging Op only) | Higher (+ OTEL Op + Loki Op + COO) |
| Data model fidelity | Lossy | Full |
| Trace correlation | Manual | Automatic |
| Cross-signal correlation | Limited | Full |
| Red Hat's strategic direction | Legacy (ViaQ) | Strategic (OTLP-native) [28] |
| Infrastructure overhead | None | OTEL Collector DaemonSet |
| Python logs auto-instrumentation | N/A | Disabled by default, must opt in [37] |

### Strategic Context

Red Hat is moving OpenShift toward being an "OTLP-native platform" [28]. The default
LokiStack data model will change from ViaQ to OpenTelemetry in future releases [22].
This signals that Option B is the long-term direction, even though Option A is more
mature today.

### Practical Recommendation

**Start with Option A** if you need production-ready logging today and your primary
requirement is shipping logs to the OpenShift logging stack. This approach:
- Uses only GA components
- Requires no additional operators
- Works with the existing Logging Operator + LokiStack setup
- Gets trace context into logs via `OTEL_PYTHON_LOG_CORRELATION=true` [5]

**Plan for Option B** as the OTLP path matures. When OTLP output from the CLF exits
Technology Preview and the LokiStack data model defaults to OpenTelemetry, migrating
to the full OTEL pipeline will provide automatic trace correlation, cross-signal
correlation, and better query performance [23].

**If you also need traces and metrics** through OTEL (not just logs), Option B becomes
more attractive now — the OTEL Collector is already the standard path for those signals,
and adding logs to the same pipeline provides unified observability [32][38].

## Limitations of This Analysis

- The OTEL Python logging SDK remains **experimental** (`opentelemetry.sdk._logs`) —
  APIs may change in minor releases [3]
- OTLP output from the OpenShift ClusterLogForwarder is **Technology Preview** across
  all current Logging 6.x releases [19][21]
- The `opentelemetry-instrumentation-logging` package is relatively new (post-1.40.0)
  and replaces the deprecated handler in the SDK [4][5]
- No production-ready file exporter exists in the Python SDK [11]
- Research conducted March 2026; the OTEL and OpenShift logging landscapes are evolving
  rapidly
