## 1. The "Modular Monolith" Pattern

### Definition
A modular monolith structures an application as a single deployment unit while internally dividing it into distinct, loosely coupled modules. Each module encapsulates specific business functionality and interacts with others through well-defined interfaces.

### Key Advocates and Sources

**Kamil Grzybek** — Author of the "Modular Monolith: A Primer" series and a GitHub reference implementation combining modular monolith with DDD.
- URL: https://www.kamilgrzybek.com/blog/posts/modular-monolith-primer
- GitHub: https://github.com/kgrzybek/modular-monolith-with-ddd
- Claim: "We rarely exchange the database access layer, logging library or GUI framework. For this reason, the module in the Modular Monolith is a business module that is able to fully provide a set of desired features."
- Claim: Modules must have well-defined interfaces (Contracts), and all communication between modules should only take place through these interfaces.
- Credibility: High — detailed series with code-backed reference implementation.

**Chris Richardson (microservices.io)** — Advocate of modular monolith patterns for fast flow.
- URL: https://microservices.io/post/architecture/2024/09/09/modular-monolith-patterns-for-fast-flow.html
- Claim: Domain-driven modules should be organized based on DDD subdomains/bounded contexts rather than technical layers.
- Credibility: Very High — author of canonical microservices patterns book.

**Spring Team (Spring Modulith)** — Canonized the pattern in the Spring/Java ecosystem.
- URL: https://junkangworld.com/blog/5-game-changing-spring-modulith-20-features-for-2025
- Claim: Spring Modulith allows developers to "avoid the premature complexity of microservices while escaping the chaos of a traditional 'big ball of mud' monolith."
- Spring Modulith 2.0 projected features include dynamic module loading, AI-assisted boundary enforcement, and enhanced event-driven communication.
- Credibility: High — official Spring ecosystem project.

**Google** — Published "Towards Modern Development of Cloud Applications" (HotOS'23).
- PDF: https://pages.cs.wisc.edu/~rgrandl/papers/ms.pdf
- Authors: Sanjay Ghemawat, Robert Grandl, Srdjan Petrovic, Michael Whittaker et al.
- Claim: "Microservices conflate logical boundaries (how code is written) with physical boundaries (how code is deployed)."
- Data: Prototype of 11 microservices ported to monolith with components — reduced from 78 cores to 9 cores (all components colocated), median latency dropped to 0.38ms. Described as "15x reduction in latency and saved costs by 10x."
- Led to open-source framework **Service Weaver** — write as monolith, deploy as microservices.
- Credibility: Very High — Google research, peer-reviewed conference paper.

**Academic Research** — Systematic literature review published October 2025 (MDPI Future Internet).
- URL: https://www.mdpi.com/1999-5903/17/11/496
- Title: "Modular Monolith Architecture in Cloud Environments: A Systematic Literature Review"
- Claim: From 369 retrieved records, only 15 primary studies were included, indicating academic research on modular monolith architecture "remains fragmented and lacks systematic synthesis."
- Credibility: Very High — peer-reviewed journal.

### Major Example: Shopify

- URL: https://shopify.engineering/shopify-monolith
- URL: https://www.infoq.com/news/2019/07/shopify-modular-monolith/

## 2. Martin Fowler's "MonolithFirst" Guidance

### Primary Source
- URL: https://martinfowler.com/bliki/MonolithFirst.html
- Date: June 2015
- Author: Martin Fowler

### Key Arguments

1. **YAGNI**: "When you begin a new application, how sure are you that it will be useful to your users? It may be hard to scale a poorly designed but successful software system, but that's still a better place to be than its inverse."

2. **Microservice Premium**: "Microservices are a useful architecture, but even their advocates say that using them incurs a significant 'MicroservicePremium,' which means they are only useful with more complex systems."
   - Related article: https://martinfowler.com/bliki/MicroservicePremium.html

3. **Getting Boundaries Right**: "Microservices only work well if you come up with good, stable boundaries between the services. Any refactoring of functionality between services is much harder than it is in a monolith. But even experienced architects working in familiar domains have great difficulty getting boundaries right at the beginning."

4. **Execution Strategy**: "The logical way is to design a monolith carefully, paying attention to modularity within the software, both at the API boundaries and how the data is stored. Do this well, and it's a relatively simple matter to make the shift to microservices."

### Fowler's Own Caveat
He expressed skepticism, noting "he'd feel much more comfortable with this approach if he'd heard a decent number of stories where it worked out that way" — i.e., successfully transitioning from monolith to microservices. He acknowledged "you cannot assume you can take an arbitrary system and break it into microservices — most systems acquire too many dependencies between their modules, and thus can't be sensibly broken apart."

### The Published Counterpoint: Stefan Tilkov — "Don't Start with a Monolith"
- URL: https://martinfowler.com/articles/dont-start-monolith.html
- Date: 2015
- Also: https://www.infoq.com/news/2015/06/monolith-vs-microservices/
- Published on Fowler's own site as a direct rebuttal.

Key quotes from Tilkov:
- "I'm firmly convinced that starting with a monolith is usually exactly the wrong thing to do."
- "If you are actually able to build a well-structured monolith, you probably don't need microservices in the first place."
- "A monolith won't magically contain services waiting to be liberated."
- Argues microservices' main benefit is "enabling parallel development by establishing a hard-to-cross boundary between different parts of your system."
- "The basic idea of a monolith is to couple things to each other." From a technical view, all parts share the same platform, abstractions, and libraries. This increases coupling, and "it's extremely hard to pull apart an existing monolith."
- Proposes "Self-Contained Systems" (SCS) — autonomous services larger than microservices but responsible for one business domain.
- Credibility: High — published on Fowler's own site, Tilkov is founder of INNOQ.

### Current Relevance
The article remains widely cited in 2025-2026. The modular monolith movement has essentially become the practical implementation of "MonolithFirst" — start monolithic with strong internal boundaries, decompose later only if needed.

## 3. Strangler Fig Pattern for Gradual Decomposition

### Origin
- Coined by **Martin Fowler in 2004** during a vacation in Queensland rain forests.
- Original URL: https://martinfowler.com/bliki/StranglerFigApplication.html
- Preserved original text: https://martinfowler.com/bliki/OriginalStranglerFigApplication.html
- Quote: "Gradually create a new system around the edges of the old, letting it grow slowly over several years until the old system is strangled."
- Name was changed from "Strangler Application" to "Strangler Fig Application" because Fowler "became concerned about its connotations of violence." He noted "the new title strangled the old one."
- Credibility: Very High — Martin Fowler, ThoughtWorks Chief Scientist.

### How It Works
A facade/proxy intercepts requests to the legacy system and routes them either to the legacy application or to new microservices. Over time, more functionality moves to new services until the monolith can be decommissioned.

The fundamental strategy is **Event Interception**, which can be used to gradually move functionality and enable **AssetCapture**.

### Key Benefits
- Delivers value incrementally — "you benefit from microservices almost immediately, as soon as you have the first service"
- Reduces migration risk — rollbacks are easier
- "Gives you the flexibility to pause the modernization if higher priority feature development needs to be done"
- Monolith continues functioning during transition — no disruption to user experience
- New features can be implemented directly as services

### Key Risks and Considerations
- **Proxy as SPOF**: "This proxy layer can become a single point of failure or a performance bottleneck"
- **Data handling**: "One of the trickiest parts of the strangler pattern is handling data. The monolith has its own database, and the new microservice might use a different one."
- **Code base access required**: "You must have access to the monolith application's code base. As features are migrated out, you will need to make minor code changes and implement an anti-corruption layer."
- **Cultural shift**: "Migrating to microservices isn't just a technical change; it's also a cultural one."

### Why Not a Big Bang Rewrite?
- URL: https://microservices.io/post/refactoring/2023/06/21/strangler-fig-application-pattern-incremental-modernization-to-services.md.html
- "A big bang rewrite delivers no value until the very end when it's completed."
- "A big bang rewrite is chasing a moving target. And like any large project it's likely to take far longer than planned."

### Platform Documentation
- AWS: https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/strangler-fig.html
- Azure: https://learn.microsoft.com/en-us/azure/architecture/patterns/strangler-fig
- microservices.io: https://microservices.io/patterns/refactoring/strangler-application.html
- Confluent: https://developer.confluent.io/patterns/compositional-patterns/strangler-fig/
- Baeldung: https://www.baeldung.com/cs/microservices-strangler-pattern

### Case Study: BestBuy.com
- URL: https://komodor.com/learn/monolith-to-microservices-5-strategies-challenges-and-solutions/
- Claim: BestBuy.com leveraged the strangler pattern to manage holiday traffic peaks. Gradually introduced microservices and validated performance, modernized without disrupting user experience.
- Credibility: Medium — secondary source (Komodor blog).

## 4. When to Decompose: Team Size, Scale, and Organizational Signals

### Sam Newman (Author of "Building Microservices" and "Monolith to Microservices")
- URL: https://www.infoq.com/news/2020/05/monolith-decomposition-newman/
- URL: https://www.infoq.com/podcasts/monolith-microservices/
- Book: https://samnewman.io/books/monolith-to-microservices/

Key findings:
- Primary signal: **Delivery contention** — "they have lots of developers working on a given problem, and those developers are getting in each other's way."
- Quote: "Microservices are not a good choice for most startups."
- Quote: Most companies would do better with "the highly underrated option of a modular monolith" than with microservices.
- No specific team size number prescribed. Focus is on coordination cost exceeding benefit.
- Recommends incremental approach: "I don't have a big shopping list of things that I say that people have to do."
- Noted modular monolith "uses ideas from the 1970s like structured programming."
- Credibility: Very High — literally wrote the canonical microservices book.

### Chris Richardson (microservices.io)
- URL: https://microservices.io/post/refactoring/2020/08/21/ten-principles-for-refactoring-to-microservices.html
- URL: https://microservices.io/post/refactoring/2020/07/28/six-principles-for-refactoring-to-microservices.html
- Principle #1: **"Don't"** — don't decompose your monolith unless you truly need to.
- Claim: "Monolith is not actually an anti-pattern."
- Microservices best adopted later once application needs to be scaled, not from the beginning.
- Credibility: Very High — author of Microservice Patterns book.

### Martin Fowler
- URL: https://martinfowler.com/articles/break-monolith-into-microservices.html
- Signals: Organizations want to "increase the scale of operation and accelerate the pace of change" and "grow their number of teams while enabling them to deliver value in parallel."
- Recommendation: Start by building out infrastructure and CI/CD pipelines with the first decomposed services. Begin with capabilities that are fairly decoupled from the monolith.
- Credibility: Very High.

### Organizational Signals (Aggregated from multiple sources)
1. **Deployment friction**: Multiple teams must coordinate for single releases
2. **Cascading changes**: Changes in one area unpredictably affect others
3. **Single points of failure (human)**: Specific engineers become bottlenecks for critical subsystems
4. **Sublinear scaling**: Doubling headcount does not double output — most incremental effort goes to managing dependencies
5. **Communication overhead**: Teams spend more time coordinating than delivering features (described as "a kind of human Amdahl's law")

### Team Size Thresholds (from decision frameworks)
- URL: https://medium.com/@kittikawin_ball/microservices-vs-monoliths-architecture-decision-framework-for-2025-98c8ff2ec484
- URL: https://www.javacodegeeks.com/2025/12/microservices-vs-monoliths-in-2026-when-each-architecture-wins.html
- Consensus thresholds from multiple independent sources:
  - **1-10 developers**: Monolith. Microservices overhead slows you down.
  - **10-50 developers**: Modular monolith. Structure without distribution complexity.
  - **50+ developers**: Microservices become beneficial as coordination costs justify the investment.
- Claim: "Microservices require 3 to 5 developers per service to maintain properly. A 15-person team managing 12 services isn't being agile; they're drowning."
- Credibility: Industry analysis blogs; multiple independent sources converge on similar thresholds.

### When NOT to Decompose
- Early-stage startups or prototypes
- Systems with unclear domain boundaries
- When building the first version of an application
- When a single team or small number of teams can effectively work in the same codebase

## 5. Successful Monolith-to-Microservices Migration Case Studies

### Netflix
- URL: https://www.hys-enterprise.com/blog/why-and-how-netflix-amazon-and-uber-migrated-to-microservices-learn-from-their-experience/
- **Trigger**: Massive breakdown in **2008** causing several days of downtime.
- Also driven by rapidly increasing data that was hard to store in existing data centers.
- Migrated to AWS, broke monolith into **700+ microservices**.
- Timeline: First step in 2009 — migrated non-customer-facing movie-coding platform as independent microservice. Spent two years converting customer-facing systems; finalized in **2012**.
- Credibility: High — widely documented, though this specific source is a secondary analysis.

### Amazon
- URL: https://www.hys-enterprise.com/blog/why-and-how-netflix-amazon-and-uber-migrated-to-microservices-learn-from-their-experience/
- **Trigger**: Scaling challenges in the growing online marketplace.
- Introduced "two-pizza team" rule — no team too large to feed with two pizzas.
- "You build it, you run it" philosophy.
- Service-level agreements (SLAs) defined expectations for reliability and performance.
- Credibility: High — well-known industry history.

### Uber
- URL: https://www.hys-enterprise.com/blog/why-and-how-netflix-amazon-and-uber-migrated-to-microservices-learn-from-their-experience/
- **Trigger**: Rapid expansion beyond San Francisco; monolith could not support new cities and services.
- Shifted to microservices in **2014**.
- Scaled to **over 1,000 services**, many with tangled dependencies — engineers referred to architecture as the **"Death Star."**
- Built own service mesh: **Uber Catalyst**.
- Credibility: High — well-known industry history.

### Agoda (Client-First Approach)
- URL: https://medium.com/agoda-engineering/leading-with-clients-our-journey-to-microservices-from-a-graphql-monolith-252b8baa69af
- Migrated from a complex GraphQL monolith.
- Innovation: Prepared clients first to handle both monolith and microservices, achieving **zero code change on the client side** when moving traffic.
- Credibility: High — first-party Agoda engineering blog.

### Common Triggers Across All Cases
- Rapid growth outpacing monolithic architecture
- Deployment bottlenecks — deploying everything at once
- Scaling difficulties — inability to scale individual components
- Need for independent team autonomy
- Development velocity degradation as codebase grew

- URL: https://nglogic.com/9-most-common-mistakes-when-migrating-from-monolith-to-microservices/

- Credibility: Medium — industry blog.

### Common Failure Patterns
1. **Rushing without preparation**: Distributed architecture's complexity means "it's not ideal for certain types of organizations or applications"
2. **Tight coupling**: Teams maintain coupling from monolithic design across service boundaries
3. **Wrong sizing**: Services too small = nanoservices; more services than can be managed
4. **Data challenges**: "Data separation is the hardest phase of any microservices migration" — shared databases are most common source of hidden coupling
5. **Underestimating costs**: "Even if the microservices strategy turns out to be a success, it still means a heavy hit on the pocket for maintenance"
6. **Big bang approach**: "An incremental migration strategy prioritizing small, reversible changes is low-risk. Avoid 'big bang' modernization efforts."

## 7. The Cost of Premature Decomposition

### Operational Cost Multiplier
- URL: https://itoutposts.com/blog/microservices-decomposition-strategy/
- Claim: Some teams discover microservices cost **3x more to operate**.
- Credibility: Medium — industry blog.

### Network Overhead & Reliability Degradation
- URL: https://systemdr.substack.com/p/microservice-decomposition-strategies
- A monolith's method call (microseconds, deterministic) becomes a network request (milliseconds, probabilistic).
- Claim: "One 99.9% reliable service becomes 99% reliable when called ten times" — failure probabilities multiply exponentially across service hops.
- Requires circuit breakers, timeouts, fallback strategies.
- Credibility: Medium-High — technical Substack with mathematical reasoning.

### The Distributed Monolith Anti-Pattern
- URL: https://systemdr.substack.com/p/microservice-decomposition-strategies
- Claim: "Most decomposition failures stem from shared databases. When OrderService and InventoryService share the products table, you haven't created microservices — you've created a distributed monolith."
- Credibility: Medium-High.

### Wrong Boundaries = Costly Rework
- Claim: "If you need distributed transactions (saga patterns, two-phase commit) across services, your boundaries are wrong. Real bounded contexts have natural transaction boundaries."
- Credibility: Medium-High — widely repeated principle.

### Google's Performance Data on Microservices Overhead
- URL: https://pages.cs.wisc.edu/~rgrandl/papers/ms.pdf
- For 10K queries/second: 11 microservices used **78 cores**; same application as monolith with colocated components used **9 cores**.
- Overhead from serialization, network calls, and distributed system management.
- Described as "15x reduction in latency and 10x cost savings" when moving to monolith.
- Credibility: Very High — Google research paper (HotOS'23).

### Infrastructure Prerequisites (Without Which Decomposition Adds Only Cost)
- URL: https://martinfowler.com/articles/break-monolith-into-microservices.html
- Requires: on-demand deployment environments, new CI/CD pipelines for independent build/test/deploy, ability to secure/debug/monitor distributed architecture.
- Credibility: Very High — Martin Fowler.

### Team Structure Must Match
- Claim: "Microservices require autonomous teams owning end-to-end service lifecycles — development, deployment, on-call rotation, and support. Decompose services to match team boundaries, not the other way around."
- URL: https://systemdr.substack.com/p/microservice-decomposition-strategies
- Credibility: Medium-High.

### Rewrite Over Reuse
- Claim: "In majority of the decomposition scenarios, the teams are better off to rewrite the capability as a new service and retire the old code" — due to high cost and low value of reuse from boilerplate and environmental dependencies.
- URL: https://www.kloia.com/microservice-decomposition-strategy
- Credibility: Medium — industry blog.

## 8. Reversibility: Microservices Back to Monolith

### Academic Overview
- URL: https://www.mdpi.com/2079-9292/13/8/1452
- Title: "From Microservice to Monolith: A Multivocal Literature Review" (MDPI Electronics, April 2024)
- Four documented cases of switching back: **Istio control plane, Amazon Prime Video monitoring service, Segment, and InVision**.
- Five main reasons for switching back: **cost, complexity, scalability, performance, and organization**.
- Six key aspects of switching-back process: (1) stop developing more services, (2) consolidate and test paths, (3) unify data storage, (4) implement message bus principle, (5) give up diverse techniques, (6) learn modular design principles.
- Credibility: High — peer-reviewed journal.

### Amazon Prime Video (2023)
- URL: https://dev.to/indika_wimalasuriya/amazon-prime-videos-90-cost-reduction-throuh-moving-to-monolithic-k4a
- URL: https://devclass.com/2023/05/05/reduce-costs-by-90-by-moving-from-microservices-to-monolith-amazon-internal-case-study-raises-eyebrows/
- URL: https://thenewstack.io/amazon-prime-videos-microservices-move-doesnt-lead-to-a-monolith-after-all/
- Service: Video quality monitoring for live streams (NOT the main Prime Video streaming service).
- Original architecture: AWS Step Functions + S3 intermediate storage. Hit "a hard scaling limit at around 5% of the expected load" and "cost of all the building blocks was too high."
- Solution: Consolidated into single monolithic application. Data transfer moved to in-memory, eliminating S3.
- Result: **Reduced infrastructure cost by over 90%** and improved performance.
- **Important nuance** — Adrian Cockcroft (former VP of Cloud Architecture at AWS): "This definitely isn't a microservices-to-monolith story. It's a Step Functions-to-microservices story. And I think one of the problems is the wrong labeling."
- Werner Vogels (Amazon CTO): "Building evolvable software systems is a strategy, not a religion. And revisiting your architectures with an open mind is a must."
- Credibility: Very High — primary source is Amazon's own engineering team.

### Segment (Twilio)
- URL: https://www.twilio.com/en-us/blog/developers/best-practices/goodbye-microservices
- URL: https://www.infoq.com/news/2020/04/microservices-back-again/
- URL: https://www.infoq.com/news/2018/07/segment-microservices/
- Timeline: Started monolith (2013) -> moved to microservices (one worker per destination) -> moved back to monolith.
- Reason for microservices: Lack of isolation — problems connecting to one destination affected all destinations.
- System sprawled to **140+ services**, each in its own repository.
- During hypergrowth (2016-2017), added **50+ new destinations** (~3 per month).
- Quote: "It seemed as if they were falling from the microservices tree, hitting every branch on the way down."
- Quote: "As their velocity plummeted, their defect rate exploded."
- Conway's Law failure: "This Segment team was 3 people and 140 services. Microservices are best at solving org coordination issues where teams step on each other. This is a case of a team stepping on itself."
- Versioning chaos: "Engineers, pressed for time, would only update libraries for the one service they were working on."
- The "distributed monolith" diagnosis: "If you must deploy every service because of a library change, you don't have services, you have a distributed monolith."
- Solution: Consolidated all 140+ services into single monolithic service called **Centrifuge**, moved all code into monorepo.
- Results: In 2016 (microservices), 32 library improvements. After monolith, **46 improvements in six months alone** — more in six months than all of 2016.
- Large worker pool absorbed spikes — no longer paged for low-volume destinations.
- Quote (Alexandra Noonan): "If microservices are implemented incorrectly or used as a band-aid without addressing some of the root flaws in your system, you'll be unable to do new product development because you're drowning in the complexity."
- Credibility: Very High — first-party Twilio engineering blog.

### Istio Control Plane
- URL: https://istio.io/latest/blog/2020/istiod/
- URL: https://blog.christianposta.com/microservices/istio-as-an-example-of-when-not-to-do-microservices/
- IEEE paper: https://ieeexplore.ieee.org/document/9520758/
- ResearchGate: https://www.researchgate.net/publication/351248643_The_Monolith_Strikes_Back_Why_Istio_Migrated_From_Microservices_to_a_Monolithic_Architecture
- Originally built as separate microservices: Pilot (discovery), Galley (config), Citadel (certs), Mixer (extensibility).
- Consolidated into single binary **istiod** in Istio 1.5.
- Quote: "The complexity of the microservices approach proved to not deliver the value or goals it intended."
- Key insight: "Control plane costs were dominated by a single feature (serving XDS). Every other control plane feature had a marginal cost by comparison, therefore there was little value to separation."
- Operational reality: "A single group (or even single person) operates the Istio control plane."
- Internal modular structure preserved within the monolith binary — "istiod is an incarnation of a monolith which supports all of the functionality of the previous releases with significantly reduced complexity."
- Broader lesson: "Does this change imply that microservices are a mistake for all workloads? Of course not. They are a tool in a toolbelt, and they work best when they are reflected in your organizational reality."
- Credibility: Very High — official Istio blog + IEEE publication.

### DHH's "How to Recover from Microservices" (May 2023)
- URL: https://world.hey.com/dhh/how-to-recover-from-microservices-ce3803cc
- 5-step recovery guide:
  1. **Stop digging** — no new microservices. Pick one existing service as epicenter to swallow others.
  2. **Consolidate critical, dependent paths first** — signup, checkout, content viewing. "That's where microservices cause the most harm."
  3. **Leave isolated performance hotspots for last** — narrow, isolated, performance-critical segments that may benefit from a different language.
  4. **Drop the most esoteric implementations** — "3-5-7 different programming languages, even more diverse frameworks" is "murder for conceptual comprehension."
  5. **Partition with modules rather than networks**.
- Quote: "The vast majority of systems should have no more than two backend languages: a general-purpose language tuned for programmer productivity for 99% of use, and a high-performance language for the last 1%."
- References GitHub and Shopify as monoliths with "millions of lines of code and thousands of programmers."
- Credibility: High — DHH is Rails creator and long-time practitioner.

## 9. DDD and Bounded Contexts as Prerequisite for Decomposition

### Martin Fowler — Bounded Context Definition
- URL: https://martinfowler.com/bliki/BoundedContext.html
- "Bounded Context is a central pattern in Domain-Driven Design. It is the focus of DDD's strategic design section, which is all about dealing with large models and teams."
- "DDD deals with large models by dividing them into different Bounded Contexts and being explicit about their interrelationships."
- "As you try to model a larger domain, it gets progressively harder to build a single unified model. Different groups of people will use subtly different vocabularies in different parts of a large organization."
- Credibility: Very High.

### Bounded Contexts are NOT Microservices (Vlad Khononov)
- URL: https://vladikk.com/2018/01/21/bounded-contexts-vs-microservices/
- URL: https://medium.com/@vladikk.com/bounded-contexts-are-not-microservices-ead44b8d6e35
- Claim: "A Bounded Context is the exact opposite of a Microservice! A Bounded Context defines the boundaries of the biggest services possible — services that won't have any conflicting models inside of them."
- "If you follow the Bounded Context strictly, you will get monoliths. Those will be 'good' monoliths, since there won't be any conflicting models in them, but still, they are not Microservices."
- "A Microservice is a Bounded Context, but not vice versa. Not every Bounded Context is a Microservice."
- Mapping options: one-to-one (ideal), one-to-many (BC split into multiple services), many-to-one (multiple BCs consolidated).
- Credibility: High — Vlad Khononov is author of "Learning Domain-Driven Design" (O'Reilly).

### Microsoft Azure Guidance
- URL: https://learn.microsoft.com/en-us/azure/architecture/microservices/model/domain-analysis
- "The biggest mistake teams make when building microservices is splitting by technical layers — a service for the database, a service for the API, a service for notifications. This creates tight coupling and leads to distributed monoliths."
- Recommends: "Split by business capability. Each microservice maps to a bounded context."
- DDD has strategic phase (large-scale structure) and tactical phase (entities, aggregates, domain services).
- Credibility: High — official Microsoft documentation.

### DDD as Prerequisite — Practical Patterns
- URL: https://www.infoq.com/presentations/microservices-ddd-bounded-contexts/
- Title: "Practical DDD: Bounded Contexts + Events => Microservices"
- "When you combine the discipline of domain-driven design and then use a technology like messaging to communicate between bounded contexts, you naturally land up in a land of microservices."
- **Event Storming** recommended as collaborative workshop technique to identify domain events, subdomains, bounded contexts, and aggregate boundaries before decomposition.
- Credibility: High — InfoQ conference presentation.

### Kamil Grzybek's Implementation
- URL: https://www.kamilgrzybek.com/blog/posts/modular-monolith-domain-centric-design
- URL: https://www.kamilgrzybek.com/blog/posts/modular-monolith-integration-styles
- "Since the module should be domain-oriented (see Bounded Context concept from DDD strategic patterns set), we can use the domain-centric architecture on the level of the module itself."
- Domain Events are local to a Bounded Context; Integration Events cross boundaries and should be "as small as possible" as they are "part of the contract made available by the given module."
- Credibility: High — detailed series with reference implementation.

### Key Takeaway
Without understanding bounded contexts first, teams risk creating distributed monoliths. DDD provides the prerequisite domain analysis that identifies natural business boundaries before service decomposition. As one source summarized: "DDD describes how business should be divided into bounded contexts, the Modular Monolith and its modularization tell us how to structure it as code."

## 10. "Majestic Monolith" Concept (DHH/Basecamp)

### Primary Source
- URL: https://signalvnoise.com/svn3/the-majestic-monolith/
- Author: David Heinemeier Hansson (DHH), creator of Ruby on Rails, co-founder/CTO of Basecamp (37signals)

### Core Definition
- "An integrated system that collapses as many unnecessary conceptual models as possible, eliminating as much needless abstraction as you can swing a hammer at."

### Why Basecamp Uses It
- "With very broad scope, deep commitments, and a very small budget (comparably speaking), the necessity of this situation simply isn't compatible with a highly labour-intensive pattern like microservices/SOA."
- Code quality mission: "Such a mission is simply not compatible with an accidental monolith. It just gotta be majestic."
- Design pressure: "This puts immense pressure on making the application understandable and changeable by individuals, not teams, which in turn forces you to take the time to turn a long letter into a short one."

### DHH's Advice
- Quote: "Run a small team, not a tech behemoth? Embrace the monolith and make it majestic. You Deserve It!"
- References GitHub and Shopify as monoliths with "millions of lines of code and thousands of programmers."
- Quote: "If you don't have many more millions of lines of code or thousands of programmers, exercise extreme caution before even thinking about microservices."
- On X (2018): "The Majestic Monolith is one of the most powerful, productive patterns in all of software development."
  - URL: https://x.com/dhh/status/962452557502201856
- On X (October 2025): "The majestic monolith remains undefeated for the vast majority of web apps. Replacing method calls with network calls makes everything harder, slower, and more brittle. It should be the absolute last resort."
  - URL: https://x.com/dhh/status/1981342407129235683

### The Citadel Evolution
- URL: https://signalvnoise.com/svn3/the-majestic-monolith-can-become-the-citadel/
- Keeps the Majestic Monolith at the center, but supports it with **Outposts** — small extracted services for organizational, performance, or implementation reasons.
- Not full microservices; selective extraction only when clearly warranted.

### Basecamp 4
- URL: https://world.hey.com/dhh/building-basecamp-4-405a347f
- "All the great ideas for Basecamp 4 fit as a continuation of the product design put in place with Basecamp 3, and the technical architecture is in great shape."
- Basecamp 4 did not need to be a rewrite — the monolith architecture continued to serve.

### Applicability
Best suited for:
- Small-to-medium teams
- Companies where "individual comprehension" of the entire system is valued
- Products with broad scope but relatively small engineering teams
- Organizations prioritizing code quality and developer happiness

Less applicable when:
- Thousands of engineers need to work independently
- Individual components have radically different scaling requirements
- Regulatory/security isolation is mandatory for specific subsystems

### Related Voice: Kelsey Hightower
- URL: https://changelog.com/posts/monoliths-are-the-future
- Former principal engineer at Google Cloud.
- Quote: "Monoliths are the future because the problem people are trying to solve with microservices doesn't really line up with reality."
- Quote: "If people would just start with organized modular code, we can make the deployment architecture an implementation detail."
- Credibility: Very High.
